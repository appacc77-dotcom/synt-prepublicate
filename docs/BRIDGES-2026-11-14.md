**Дата:** 14.11.2026
**Задача:** два полноценных подключения к источнику макета, полная сверка сайта через них,
замеры скорости и список вопросов.

## 1. Что сделано

| Что | Где |
|---|---|
| Контракт моста (5 функций, общая форма узла) | [`tools/bridges/README.md`](../tools/bridges/README.md) |
| Мост к **Figma desktop** (плагин + брокер `figma-agent`) | [`tools/bridges/figma-desktop/`](../tools/bridges/figma-desktop/index.mjs) |
| Мост к **FigCraft** (`figcraft-cli mcp`, JSON-RPC по stdio) | [`tools/bridges/figcraft-cli/`](../tools/bridges/figcraft-cli/index.mjs) |
| Единый CLI | `node tools/bridge.mjs <figma\|figcraft> <status\|pages\|tree\|png\|timing>` |

Оба моста отдают **одну форму**: плоский список узлов с путём из имён, типом, координатами
от родителя, размером и текстом. `id` мостов разные и не сравниваются — ключ сверки только путь.

Форма проверена: на Home до глубины 3 оба моста дали **одинаковые 142 пути с одинаковыми
координатами** (main 2455,0 1440×10548; hero 0,0 1440×780; banner y=780; pain y=1305).

## 2. Скорость (машина автора, 14.11.2026)

### 2.1 Повторные чтения: desktop быстрее, FigCraft дешевле в пике

| Операция | Figma desktop (файл `Website Syntonia-2` открыт) | FigCraft CLI (архив `.fig` 103 МБ) |
|---|---:|---:|
| статус / открытие файла | 206 мс | 1 372 мс (один раз на процесс) |
| список страниц | 236 мс | 1 мс (файл уже открыт) |
| дизайн-система (компоненты/токены/стили) | 247 мс (56 / 41 / 39) | — (нужен отдельный вызов `inspect_document`) |
| дерево Home до глубины 6 | 371 мс (1 260 узлов) | 456 мс (1 272 узла, ответ 214 КБ) |
| PNG hero 1440×780 | 1 122 мс (999 774 Б) | 196 мс (1 296 984 Б) |
| **Итого четыре шага** | **2 182 мс** | **2 025 мс** |

Вывод: **разница в суммарной скорости незначительна**. Desktop выигрывает на повторных чтениях
(файл уже открыт в приложении), FigCraft — на рендере PNG и на независимости от окна. Для конвейера
с 49 секциями это значит: выбор моста определяется не скоростью, а достоверностью и удобством.

### 2.2 Тяжёлые операции desktop-моста

| Операция | Время | Объём |
|---|---:|---|
| полный дамп документа (`npm run document`) | 12 563 мс | 4,36 МБ, 5 552 привязки к токенам, 51 эффект |
| `inspect --node` (скриншот окна, а не экспорт) | 12 374 мс | 999 774 Б |
| `export-png` того же узла | 1 122–1 726 мс | 999 774 Б |

`inspect` в 7–11 раз дороже `export-png` при том же результате — для кропов использовать только
`export-png`.

### 2.3 Замеры скорости без контроля очереди бессмысленны

Во время замеров мост был занят чужим прогоном (`studio-pipeline` выгружал кропы; в очереди висели
задачи `EXPORT_PNG`). В этот момент те же операции давали **3–6 с вместо 0,2–0,4 с**, а один
`exec-js` — **29,5 с вместо 0,8 с**. Отсюда правила:

1. мост сериализует операции на файле: один чужой экспорт тормозит всё;
2зависшая задача блокирует слот мутаций, снимается `figma-agent job <id> --force-release`, причём
   не всякую задачу можно снять (`is not the one blocking`), а `--force` отбрасывает результат;
3. замер надо делать на простое и указывать это в отчёте — иначе числа описывают очередь, а не мост.

Что это значит:

1. **Геометрия и текст переносятся один в один.** На 3 744 общих путях координаты и размеры

   расходится расчёт высоты авто-лейаута.
3. **Состав дерева расходится на инстансах:** у Figma на 3 175 узлов больше — это внутренности
   инстансов (`btn-primary/arrow-quiet/icon/…`, `btn-label`, группы и векторы глубин 7–10).
   FigCraft раскрывает инстанс в один узел с разрешённым видом. Для замера по `data-figma-node`
   (мы размечаем глубины ≤ 2) это неважно; для сверки инстансов — важно.

## 3.5 Пиксель по секциям: 48 из 48

Метод: [`tools/bridges/pixel-parity.mjs`](../tools/bridges/pixel-parity.mjs) — берёт эталонный кроп
секции (рендер моста Figma) и рендерит тот же узел из архива через FigCraft, затем считает ту же
метрику, что `tools/compare.mjs`.

| Метрика | Значение |
|---|---:|
| секций сверено | **48 из 48** |
| среднее по секциям | **3,74** |
| медиана | **2,29** |
| худшая | `home/pain` — 22,56 |

**Расхождение неоднородно, и причина не одна.** Три класса:

| Класс | Примеры | Числа |
|---|---|---|
| **Рендерер** (плоские секции, те же состояния) | подвалы на всех 8 страницах, `practice/hero`, `home/about-founder`, `quiz/quiz-result`, `library/library-issues` | **0,64–1,33** — практически совпадает |
| **Состояние компонента** | `home/formats` — FigCraft отрисовал слайд **2/5**, Figma — **1/5**; `home/voices` (12 состояний), шапки (16 состояний каждая) | **4,6–20,7** |
| **Эффекты и фильтры** | `home/pain` — фильтр `exposure 0,35` → 22,56; `home/faq` — `contrast 0,13` → 7,98; шапки — `BACKGROUND_BLUR` и текстура кнопки; `home/air-photo` — фото Display P3 | **6,0–22,6** |

То есть **пиксель FigCraft — не «другой рендерер», а другой рендерер плюс другие состояния плюс
неперенесённые эффекты**. Пока не сделан маппинг состояний и не сверены фильтры/эффекты, пиксельная
сверка «кроп Figma ↔ FigCraft» меряет смесь трёх причин и не годится как эталон (решение 423).

## 4. Что выяснилось про FigCraft по дороге

1. **Плагины Figma не работают** — наш «DESIGN:OS Bridge» там не запускается; подключение сделано
   отдельным модулем, а не настройкой существующего моста.
2. **Импорт `.fig` — «best effort»**: 5 классов предупреждений на нашем файле — стили векторных
   сегментов (×172), привязанные к переменным векторные заливки (×28), привязки к библиотечным
   переменным (×6), фильтры картинок рисуются приближённо (×6), переменные без читаемого значения
   пропущены.
3. **Песочница путей работает строго**: запись разрешена только в `--automation-write-root`;
   попытка писать в `/tmp` при корне `$TMPDIR` отклоняется. Модуль добавляет каталог `--out` в roots.
4. **Версии расходятся**: приложение 0.15.0, CLI 0.18.1. Headless-режим работает, но `mcp --attach`
   к приложению 0.15.0 использовать нельзя без обновления приложения.
5. **`mainComponent` в Figma запрещён синхронно** (`documentAccess: dynamic-page`) — шаблон снимка
   дерева пришлось упростить; иначе плагин падает с `E_EVAL`.

## 5. Вопросы, которые нужно решить

1. **Сверка сделана на выгруженном `.fig`** (`~/Downloads/Website Syntonia-2.fig`, 12.11 22:01).
   Для периодических сверок нужен регламент: кто и когда выгружает архив, куда его класть
   (предлагаю `design/incoming/`, путь уже есть в `.gitignore` проекта) — иначе сверка гниёт.
2. **Назначать ли FigCraft эталоном?** Ответ прежний — **нет** (решение 423): геометрия и текст
   совпадают полностью, но пиксель требует ещё маппинга состояний и сверки эффектов. FigCraft —
   второй независимый читатель `.fig` и рендер без открытого Figma.
3. **Маппинг состояний.** `formats` показал: один и тот же узел в Figma и FigCraft — разные слайды.
   Нужно решить, делаем ли маппинг «состояние Figma → вариант FigCraft» (это же нужно и для `states`
   ворот) или фиксируем FigCraft только для секций без состояний.
4. **Эффекты и фильтры.** `BACKGROUND_BLUR`, `exposure/contrast` и Display P3 не переносятся.
   Это либо ограничение FigCraft (тогда вопрос в upstream), либо требует отдельного решения по
   кропам: снимать кропы FigCraft только для секций без эффектов.
5. **Фиксировать ли версии** плагина и CLI в `project.json` с воротами (сейчас приложение 0.15.0,
   CLI 0.18.1).
