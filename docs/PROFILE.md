# Профиль прогона: что занимает время

Замер сделан на ветке `verify/full-run-2026-11-11`, 11.11.2026, Mac, холодный
прогон без кэша: `node tools/conveyor.mjs check --all`.

Числа берутся из артефактов, а не по секундомеру на глаз:
`reports/runs/<id>/verdict.json` пишет `ms` для каждого шага, сумма шагов
сверяется с общим временем — разница это накладные расходы конвейера.

## Итог

| | было | стало |
|---|---:|---:|
| полный прогон (этап 1) | 46.8 с | **20.8 с** |
| `interactive` | 24.3 с | **9.5 с** |
| `measure` | 5.4 с | **2.3 с** |
| `stretch` | 8.9 с | **1.7 с** |
| накладные конвейера | 0.7 с | 0.6 с |

Кэш не помогает: `check --all --cache` даёт те же ~48 с — в профиле приёмки
ни один шаг не пропускается, кэшировать нечего.

## Шаги по времени

| шаг | время | доля | что делает |
|---|---:|---:|---|
| `interactive` | 9.5 с | 47 % | нажимает все элементы управления на семи страницах |
| `measure` | 2.3 с | 11 % | сверяет геометрию 47 секций |
| `stretch` | 1.7 с | 8 % | сравнивает ширины на 1440 и 1512 |
| `build` | 1.5 с | 7 % | сборка Astro |
| `layout` | 1.1 с | 5 % | горизонтальная прокрутка на ширине макета |
| остальные 17 шагов | ~3.4 с | 15 % | сравнения, реестры, контракты |

Сумма шагов 20.3 с, общее 20.8 с.

## `interactive`: 24.3 → 9.2 с

Разбор по коду и замеру (инструментированная копия, по фазам):

| статья | было | стало |
|---|---:|---:|
| фиксированные паузы | **16.1 с** | 0 |
| клики | 3.8 с | 3.8 с |
| снимки подписи | 2.6 с | 2.6 с |
| ожидание изменения секции | 0.3 с | 0.3 с |

Причина была в `waitForTimeout(150)` после каждого из 113 элементов —
17 секунд независимо от того, есть ли что ждать.

**Что сделано.** Пауза убрана. Подпись переключателя снимается сразу после
клика, и только если она совпала с исходной **при уже переключённом
`aria-expanded`** — то есть элемент собираются обвинить в «меняет лишь
атрибут» — ждём 160 мс и снимаем подпись ещё раз. Платят только
подозрительные элементы, остальные идут дальше сразу.

Почему не ожидание анимаций: пробовал `getAnimations().finished` (29.7 с) и
опрос «подпись перестала меняться» (23.3 с) — оба медленнее, потому что
у нас почти у всех переключателей есть переход 160–450 мс, и ожидание конца
перехода дороже фиксированной паузы. Оба варианта откачены.

**Проверено подменой:** в `dist/index.html` добавлена кнопка, которая меняет
только `aria-expanded`. Ворота видят 114 элементов и **1 «притворяется»** —
то есть класс дефекта по-прежнему ловится. После проверки сборка
восстановлена.

## `stretch`: 8.9 → 1.8 с

Причина была не в работе, а в ожидании сети: на каждой из 14 загрузок
(7 страниц × 2 ширины) стоял `waitUntil: 'networkidle'`, а это 500 мс тишины
сети после загрузки.

**Что сделано:** `load` + `document.fonts.ready`. Шрифты нужны, потому что
дальше меряется ширина текста; после их загрузки ожидание сети ничего не
добавляет.

**Проверено:** шаг зелёный до и после, страниц и проверок столько же;
отдельный замер 8.89 с → 1.74 с.

## `measure`: 5.4 → 2.3 с

Страница и так загружалась один раз на группу, а не на секцию. Время уходило
на `waitUntil: 'networkidle'` — те же 500 мс тишины сети на каждой из семи
загрузок, что и в `stretch`.

Убрать ожидание совсем нельзя: замер, снятый сразу после `load`, дал
**24 красных узла** в `voices` и по одному в `formats` и `faq` — карусель,
слайдер и аккордеон доводят раскладку после загрузки скриптами.

**Что сделано:** ждём то, что влияет на координаты, — `document.fonts.ready`,
декодирование всех картинок и устойчивость раскладки (два одинаковых замера
`scrollHeight` и прямоугольников секций с паузой 60 мс, потолок 600 мс).

**Проверено сравнением:** `gate.json` всех 47 секций до и после совпадают по
существу — `ok`, `red`, `covered`, `markedRatio` и даже `worstDelta`
не изменились ни у одной. Отличаются только метки времени.

Тот же выигрыш получает второй этап: `base-parity` меряет дважды, и его
10.5 с складываются из двух замеров.

## Как повторить

```bash
node tools/conveyor.mjs check --all      # прогон
node tools/profile.mjs                   # таблица последнего прогона
node tools/profile.mjs --prev            # сравнение с предыдущим
```

`npm run profile` — то же самое.


## Разброс: прогон на загруженной машине

Один прогон из серии дал **97.5 с**, из них `interactive` — **86.1 с** при
обычных 9. Браузерные шаги чувствительны к нагрузке: та же проверка отдельно
проходит за 9.38 с, повторный полный прогон — 19.8 с.

Вывод для чтения чисел: сравнивать прогоны одного профиля на одной машине,
а выбросы перепроверять повтором. Это же касается порогов по времени — их
в воротах быть не должно, только по факту результата.

## Что осталось

| | |
|---|---|
| `interactive` 9.5 с | 3.8 с кликов и 2.6 с снимков подписи — следующий шаг только через один браузерный контекст на страницу |
| `base-parity` ~10.5 с | две сборки и два замера; дешевле — только потеряв смысл проверки |
| кэш в `--all` | ни один шаг не пропускается; проверить, нужен ли он вообще в этом профиле |

## Второй слой: этап 2 идёт 27.4 с

`check --profile accept-stage2` добавляет к прогону `base-parity` — и он
самый дорогой шаг второго этапа: **~10.5 с** из 27.4 с.

Почему столько: проверка собирает сайт дважды (`build:base` в `dist-base` и
обычный `build`) и **дважды** меряет все 47 секций батчем, чтобы сравнить
`gate.json` основы с основой плюс дополнения. Это 2 × (сборка ~1.5 с + замер
2.3 с) плюс копирование гейтов.

Дешевле нельзя, не потеряв смысл: сравнение двух состояний по определению
требует оба состояния. Вариант — мерить только секции, которые затронули
дополнения, — отклонён: `allowedSections` пока пуст, и проверка как раз
доказывает, что дополнения не двигают основу нигде.

|---|---:|---|
| `accept-stage1` (`--all`) | **20.8 с** | 22 шага основы |
| `accept-stage2` | **27.4 с** | 23 шага: плюс `base-parity` ~10.5 с |
