### 1.4 Релизный конвейер

Прочитано: `tools/site-export.mjs`, `tools/check-publish.mjs`, `tools/check-site-clean.mjs`, `site-files.json`, `docs/RUNBOOK.md` (§ «Публикация»), `tools/prebuild.mjs`, `tools/git-hooks/post-commit`.

**Как задумано (и это хорошо):** мастерская = весь репозиторий; выпуск = только `include` из `site-files.json` (`src/**`, `public/{img,fonts,svg}/**`, конфиги); `site-export.mjs` собирает `.site/`, пересобирает `package.json` без скриптов мастерской, строит `dist` (`RELEASE=1`), считает `sourceHash`/`distHash`, пишет манифест, кладёт результат в ветку `site` и зеркало; `check-site-clean.mjs` собирает набор в `$TMPDIR` и доказывает, что он живёт без `design/docs/reports/tools`; `check-publish.mjs` ищет отладочные страницы и требует `noindex` у `structure.html`/`ds.html`; релиз разрешён только по зелёному прогону (`latestGreenRun()` ищет `reports/runs/*/verdict.json` со `status=PASS`, `dirty=false`, `mode in (full, accept-stage2)`).

**Где ломается воспроизводимость:**
1. `reports/runs/` — в `.gitignore:28`; в клоне отсутствует. `site-export.mjs:227` — `if (!run) fail('нет зелёного прогона приёмки — публиковать нечего')`. **С чистого клона публикация невозможна по построению.** Она возможна только на машине, где остались локальные прогоны (bus factor = 1).
2. Манифест выпуска `site-manifest.json` — в `.gitignore:50`, хотя решение 398 называет манифест контрактом. Провенанс публикации хранится только в сообщении единственного коммита ветки `site` и стирается следующим `push --force`.
3. `push --force` в двух местах (`site-export.mjs:247` — ветка `site` origin, `:324` — зеркало). Обе ветки публикации содержат **по 1 коммиту** (GitHub API: mirror main — 1, site — 1) — истории публикаций нет, откат = «пересобрать старый коммит локально + зелёный прогон + force push».
4. `prefixBase()` применяется к `outDir/dist` **до обоих пушей** (`:239`, затем `:247` и `:252`). Если запустить `--base` с зеркалом по умолчанию (`site-files.json:27` → `appacc77-dotcom.github.io`, корень домена), префикс `/synt-prepublicate` попадёт и в зеркало, где он не нужен → битые ссылки на основном адресе. RUNBOOK обходит это, подменяя `--mirror` на тот же репозиторий (`docs/RUNBOOK.md:395-396`), но это ручной флаг, а не защита в коде.
5. Все параметры релиза (`--base`, `--mirror`, `--mirror-branch`, `--push`) передаются руками; в RUNBOOK зафиксировано, что первая публикация уже сломалась именно из-за забытого `--base` (`docs/RUNBOOK.md:399-400`).
6. `site-export.mjs` использует `git worktree`, `tar`, `sh` — POSIX/macOS/Linux; Windows-путь не предусмотрен.

### 4.3 BLOCKER — бренд, домен и почта: коллизия `syntonia.com` с чужим бизнесом

**Факт:** сайт использует бренд «Syntonia» и почту `hello@syntonia.com` (`Footer.astro:47`, 17 вхождений в `design/figma/live/document.json`). При этом:
- `https://syntonia.com/` → **HTTP 200, `<title>SYNTONIA ASTRAL</title>`**, португалоязычный сайт астрологии/книг (`amazon.com.br/shops/syntonia`), IP 69.30.225.21; MX домена — Google Workspace. Это **не сайт заказчика** и другое activity.
- В коде прямо зафиксировано, что адреса не подтверждены: `Footer.astro:40-43` — «Соцсетей и почты в проекте нет: адреса ведут на заглушку, пока заказчик не даст реальные… её тоже не подтвердили».
- Кастомного домена у сайта нет: `CNAME` в ветке `site` отсутствует, сайт живёт на трёх `github.io`-адресах; в документах «домен заказчика» — открытый пункт (`docs/REPORT-2026-11-12.md:65`, `docs/BACKLOG.md:158`).

**Риски:** (а) **товарный знак** — «Syntonia» уже используется одноимённым зарубежным бизнесом (книги, астрология) в смежной тематике «самопознание»; нужна проверка в Роспатенте и решение о нейминге до коммерческого запуска; (б) **почта** — письма на `hello@syntonia.com` не попадут заказчику (домен чужой), заявки/обращения теряются, а переписка уходит третьему лицу; (в) **доверие/идентификация** — сайт без собственного домена и юрлица не идентифицирует продавца (см. 4.2); (г) бренд-риск при продвижении: поисковая выдача по «Syntonia» занята чужим сайтом.

**Минимум до запуска:** проверить ТЗ, выбрать нейминг/домен, купить домен и почту, прописать CNAME и canonical, заменить `hello@syntonia.com` на подтверждённый адрес.
**Трудоёмкость:** 1–3 недели (внешние процедуры: проверка ТЗ, регистрация/покупка домена, DNS/почта).

### 4.4 BLOCKER (формально) — не выполнено условие лицензии OFL: нет текста лицензии и copyright-нотисов

**Факт:** все 6 семейств — OFL 1.1 (см. §2.6). Но в репозитории один файл `public/fonts/LICENSE.md` — **18 строк / 863 байта**, таблица «Literata…Hurricane — OFL 1.1, Google Fonts» и ссылка `https://openfontlicense.org`. **Нет полного текста OFL 1.1 и нет copyright-строк** («Copyright 2017 The Literata Project Authors…» и т. д.). Отдельного `OFL.txt` в `public/fonts` нет (`git ls-files | grep -iE 'license|ofl'` = только `public/fonts/LICENSE.md`).

**Требование лицензии (официальный текст OFL 1.1, openfontlicense.org):** «…provided that each copy contains the above copyright notice and this license. These can be included either as stand-alone text files, human-readable headers or in the appropriate machine-readable metadata fields…» — то есть при распространении шрифтов (а self-hosted woff2 в `public/fonts` и есть распространение) **каждая копия должна содержать и copyright-нотис, и текст лицензии**. Сайт раздаёт 33 woff2-файла с CDN, а в репозитории нет ни текста, ни нотисов → формальное несоответствие OFL. Исправляется дёшево и снимает единственный лицензионный блокер шрифтов.

**Дополнительно:** `tools/fonts.mjs:141-165` скачивает файлы из Google Fonts API и пишет только `@font-face`; `npm run fonts:check` проверяет лишь наличие файлов (присутствие), а не версию/провенанс. 2 из 6 семейств (Literata, Golos Text) **не совпадают побайтно** с текущей отдачей Google Fonts и в ~3.3 раза больше по размеру (Literata cyrillic 38 640 B против 11 264 B; Golos Text 22 028 против 6 944) — в name-таблицах при этом официальные copyright/версии Google Fonts (Literata v3.103, Golos Text v2.004), т.е. это легитимные сборки OFL, но более старой/иной ревизии. На лицензию не влияет, на воспроизводимость — влияет (ворота этого не видят).

**Минимум до запуска:** положить `public/fonts/OFL.txt` (полный текст OFL 1.1 + copyright-строки для 6 семейств), сослаться из `LICENSE.md`, добавить `public/fonts/**` в выпуск (уже включён в `site-files.json:10`), при желании — `fonts:check` с хэшами.
**Трудоёмкость:** 0.5–1 час.

## Приложение Б. Ограничения аудита

1. `web_search` в среде недоступен (нет API-ключа) — лицензии проверены прямыми HTTPS-запросами к первоисточникам (google/fonts `OFL.txt`, openfontlicense.org, name-таблицы самих woff2), это даже строже, чем вторичные страницы.
2. EXIF/IPTC проверены на выборке 4 файлов (PIL/mdls); права всё равно подтверждаются только документами, а не метаданными.
3. Оценка «изображения сгенерированы ИИ» — визуальная и требует подтверждения владельцем/дизайнером; для выводов о правах это не меняет требования (нужны документы).
4. Реальный владелец/юрисдикция заказчика известны только по `docs/decisions.md` (решение 394: «у заказчика юрлицо в России»); ИНН/наименование в репозитории отсутствуют.
5. `npm ci`/`npm run build` в этом аудите не перезапускались (по инструкции Lead); использован уже собранный `dist/`.
6. GitHub API отдаёт размер `synt-prepublicate` как `0 KB` (похоже на задержку агрегата) — поэтому размер репозитория взят из локального pack (186.89 MiB), а не из API.
