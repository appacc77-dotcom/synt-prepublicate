## 2. Как устроено (кратко)

1. **Реестр-контракт.** `tools/checks.json` — единственное описание проверок: слой (`base/enhancements/integration/common`), `scope`, входы, `dependsOn`, `resources` (figma-bridge/dist/browser), `timeoutMs`, `retryPolicy`, `outputs`, `mandatoryFor`. Профиль не зашит в коде: `stepsForProfile()` берёт проверки по `mandatoryFor` (`conveyor.mjs:388-408`). «Полный» режим — это `accept-stage1`, который в отчёт пишется как `mode: "full"` (`conveyor.mjs:891`).
2. **Движок.** `conveyor.mjs` (1 161 LOC) — последовательный запуск шагов дочерними `node`-процессами без shell (`spawn(..., {shell:false, detached:true})`, `conveyor.mjs:588-668`), таймаут на шаг из контракта (`:627`), убийство группы процессов (`:629-640`), heartbeat каждые 10 с, топологический порядок по `dependsOn` (`:368-386`), статусы **PASS / FAIL / INCOMPLETE / ERROR / BLOCKED**, политика вердикта (`evaluate`, `:685-698`): ERROR → FAIL → INCOMPLETE → PASS, «сигналы» (пиксель) в вердикт не входят.
3. **Провенанс.** `gitState()` (коммит, грязность без генерируемых файлов, `contentHash` по всем tracked-файлам) до и после прогона (`:86-103, 886-922`); `releaseEligible = PASS && mode==='full' && !dirty && commit && stable` (`:912-913`); `push-ok` + git-хук `post-commit` пушат только зелёное.
4. **Кэш.** `reports/cache/<id>.json`: ключ = хеш входов из контракта + «отпечаток инструмента» + версии Node/Playwright/таймаут (`:257-347`). Кэшируется только PASS; сборка/замер/снимки/интеграционные ворота исключены (`:268`).
5. **Файловый слой.** Почти каждый инструмент самостоятелен (решение 372/393): общий только `tools/lib/` (2 файла, 139 LOC: PNG-декодер и ZIP-читалка). Каждый `check-*` сам читает JSON, поднимает HTTP-сервер над `dist/`, запускает Chromium, печатает свой текст и выбирает exit-код.
6. **Выпуск.** `site-files.json` + `site-export.mjs` (сборка вне мастерской, манифест с коммитом/хешем/`runId`) + ворота `site-clean`, `site-contract` (решения 397–399). `npm run site:check` = `conveyor check --profile release`.

## 3. Что сделано хорошо (с доказательствами)

Это редкая зрелость для проектного конвейера.

## 4. Находки по severity

Severity: **blocker** — подрывает главное обещание («зелёный прогон = доказательство» / безопасный выпуск); **major** — заметно снижает доверие/покрытие, укусит в ближайшие недели; **minor** — гигиена, на вердикт сейчас не влияет.

### Blocker

#### B-1. Кэш может выдать PASS, не выполнив проверку (и не заметив правку самой проверки)
Кэш — штатный путь приёмки: `npm run verify` = `conveyor check --profile accept-stage1 --cache` (`package.json`), `docs/RUNBOOK.md:88` прямо называет это «воротами». При этом инвалидация сломана в трёх местах:

а) **Отпечаток инструмента считается не от того файла.** `cacheKey()` берёт `tools/<id>.mjs`, где `id` — имя проверки в реестре (`conveyor.mjs:311`), но файлы называются иначе: `id: "layout"` → шаг `tool: "check-layout"` (`conveyor.mjs:193`), `id: "site-clean"` → `check-site-clean.mjs` и т.д. Мой пересчёт всех 42 id: реальный файл `tools/<id>.mjs` есть только у 4 (`measure`, `shot`, `issues`, `fonts`), у 37 подставляется константа `'bin'`, у `scaffold` хешируется **не тот файл** — генератор `tools/scaffold.mjs` вместо проверки `check-scaffold.mjs`. Вывод: **правка кода любой из 31 проверки не инвалидирует её кэш**. Поправил проверку `overflow` — получил PASS из кэша старой проверки.

б) **Пять проверок игнорируют `.astro`-файлы.** `hashInputs()` для глоба `src/**/*.astro` оставляет в суффиксе `*` (`conveyor.mjs:284-296`: `pattern.slice(star).replace(/^\*\*?\/?/, '')` → `"*.astro"`), а сравнение идёт через `endsWith("*.astro")` → 0 файлов. Проверено запуском: `hashInputs(['src/**/*.astro'])` → `files: 0, null`. Затронуты `tokens`, `invented`, `interactive`, `motion`, `motion-manifest` (единственный «рабочий» вход у `invented` и `motion-manifest` — JSON-реестр, т.е. правки компонентов эти ворота из кэша не выбивают). Для `tokens` это прямой false-PASS: добавили в компонент `var(--несуществующий)` — ключ кэша не изменился.

в) **Кэш закоммичен и платформо-независим.** 15 файлов `reports/cache/*.json` лежат в git (`git ls-files reports/cache`), кэшируется только PASS; в ключе есть версия Node и Playwright, но **нет ОС/платформы** (`conveyor.mjs:325`). Значит PASS, снятый на macOS, может быть переиспользован на Linux/CI без запуска. `reports/cache` не входит в `GENERATED` (`conveyor.mjs:71-79`) и не в `.gitignore` — т.е. кэш ещё и делает дерево «грязным» (см. m-8).

**Почему blocker:** это не «слабый порог», а класс ошибок «ворота сказали PASS, не выполнившись». Для проекта, чья заявленная ценность — «проверяемый конвейер», это подрыв основного обещания. Вероятность: правка проверки — обычная работа, кэш включён по умолчанию в `npm run verify`.
**Стоимость починки:** ~0,5–1 день: брать путь инструмента из шага (`tool`/`bin` уже есть в `GLOBAL_STEPS`/`unitSteps`), а не из id; починить суффикс глоба; добавить `process.platform|arch` в ключ; убрать `reports/cache` из git и добавть в `.gitignore`; тест на cacheKey (сейчас его нет).

#### M-1. Публикация не обязана проходить через release-профиль; контракт выпуска принимает `accept-stage2`
- `site:release` = `node tools/site-export.mjs --push` (`package.json`); **сам `site-export` не запускает ни `conveyor check`, ни `--profile release`** — он лишь ищет в `reports/runs` последний PASS (`site-export.mjs:191, 332-345`). Отдельный `npm run site:check` (`--profile release`) существует, но ничем не принуждается.
- «Зелёным прогоном» для публикации считается **`mode` из `['full','accept-stage2']`** (`site-export.mjs:343`, `check-site-contract.mjs:51`). При этом `accept-stage2` (23 проверки) **не содержит ни одной** из release-критичных: `site-clean`, `site-contract`, `weight`, `coverage-map`, `links`, `crops`, `issues`, `fonts` (сравнение `mandatoryFor` в `checks.json`). Сам же конвейер в другом месте пишет обратное: «проверены дополнения, выпуск даёт accept-stage1» (`conveyor.mjs:958`). Два инструмента держат два разных контракта публикации.
**Стоимость:** ~0,5 дня — либо `site-export`/`site:release` сами гоняют release-профиль и требуют `mode==='full'`, либо убрать `accept-stage2` из допустимых режимов и обновить контракт.

#### M-2. Три разных «объёма»: 47 vs 48 vs 49; страница `book` публикуется без приёмки
- `project.json.acceptance` = **47** секций; `structure.json.totals.total` = **46**; каталогов со `spec.json`/`gate.json` = **49**; `status.mjs` сканирует каталоги → в `STATUS.md` пишет «**48 из 49**» (`status.mjs:17-26`); `check-base-parity` берёт все `spec.json` кроме `design-system` → **48**; `check-states` — тоже каталоги, не `acceptance`.
- Вне `acceptance` оказались `book/book-hero` и `design-system/logo-gold`. `design-system` — ок (в выпуск не едет), но **`book` — реальная страница**: `src/pages/book.astro` есть, маршрут `/book.html` в `project.json.routes`, `dist/book.html` существует (25 460 байт). Её секция не проверяется ни `measure`, ни остальными секционными воротами, при этом уезжает на сайт.
- `design-system/logo-gold` — единственный красный `gate.json` (`ok:false, marked:0 of 2`, `pixel.mean=229.66`), он вне приёмки, но именно он даёт «красных: 1» в `STATUS.md`, из-за чего статус «48 из 49» и «приёмка PASS» выглядят противоречиво.
**Почему важно:** «единица приёмки» — обещание проекта (`AGENTS.md §2.1`), а в коде четыре разных её определения. Дыра `book` — реальная: секция страницы вне ворот.
**Стоимость:** ~1 день — один источник объёма (`project.json.acceptance`, остальные читают его или явно объявляют своё подмножество), добавить `book/*` в acceptance, `design-system` исключить из статуса или пометить вне приёмки.

#### M-3. Геометрические ворота зелёные при покрытии 6,4 % узлов; ретчета/базлайна нет
`measure` требует элемент только для узлов **глубины ≤ 2** (`measure.mjs:355`) и не наказывает за низкий `markedRatio` (`:405-414`; читателей `markedRatio` в воротах нет — только `report-studio.mjs`). Факты по закоммиченным `gate.json`:
- размечено суммарно **830 из 2 144** узлов = **38,7 %**;
- **11 из 49** секций имеют `markedRatio < 30 %`; худшие: `practice/kody-practice-pay` — 16 из 249 = **6,4 %**, `practice/practice-pay` — 7,3 %, `practice/practice-package` — 7,6 %; у всех `coverage: 100`, `red: 0`, `ok: true`;
- `home/air-photo` — спека из 1 узла, замер «зелёный» по одному элементу.
При этом ворота не хранят базлайн `markedRatio` и не краснеют при его падении: удаление `data-figma-node` у узла глубины ≥3 не ломает ничего. Пиксель в вердикт не входит (см. m-4). Итог: для ~61 % узлов нет ни гейтованной геометрии, ни гейтованного пикселя — «зелёная» секция гарантирует меньше, чем читается.
**Стоимость:** ~0,5–1 день — `design/figma/coverage-baseline.json` + правило «`markedRatio` не ниже базлайна − ε» и минимум, скажем, 30 % для приёмки; запись в `checks.json`.

#### M-4. `regression`/`local` замеряют только первую секцию
`commandCheck`: для профилей `local` и `regression` набор шагов — `unitSteps(units[0])` (`conveyor.mjs:765-774`), т.е. `measure/shot/visual` **одной** секции, хотя `units` для `regression` — 22 секции из `design/figma/regression.json`, а для `local` без `--unit` — вообще все собранные. `npm run conveyor check --set regression` («быстрый контрольный прогон») проверит геометрию ровно одной секции (`home/hero` — первая в файле) и напечатает покрытие по всем. Это тихая недооценка объёма в самом частом режиме.
**Стоимость:** ~2 часа — для `regression` использовать `measureBatchStep(units)` (механизм уже есть), для `local` без юнита — запретить/сказать явно.

#### M-5. `check-changes` fail-open и обходится коммитом
Ворота обещают «изменившаяся секция требует запроса на изменение». Фактически (`check-changes.mjs:31-41`): сравнивается текущий `live/snapshot.json` со снимком **из git HEAD**; если `git show HEAD:` не удался — `exit 0` («сравнивать не с чем»). Значит:
- вне git/в мелком клоне ворота молча зелёные (fail-open);
- достаточно закоммитить новый snapshot без `changes/CR-*.md` — следующий прогон сравнит с уже закоммиченным и будет зелёным. Правило «после сдачи макет не меняется без CR» воротами не обеспечивается в принципе — только «незакоммиченный дрейф».
**Стоимость:** ~0,5 дня — сравнивать не с HEAD, а с «последним одобренным» файлом (или с baseline в `changes/`), плюс fail-closed при отсутствии git.
