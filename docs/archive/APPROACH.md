# Syntonia v2 — подход к повторной вёрстке по Figma

Дата: 04.11.2026. Статус: предложение, код ещё не начат.

Основание: анализ `syntonia-deepseek` (репозиторий, инструменты, документация),
соседней сессии по переносу «Практик» и локальной выгрузки
`design/figma/Website Syntonia.fig`.

---

## 1. Короткий вывод

Переделывать имеет смысл, но переделывать нужно **не текст и не картинки**, а
архитектуру и метод переноса.

Что сломалось в старой версии:

- сайт собран как 11 рукописных HTML-страниц с 11 копиями шапки и подвала;
- стили страниц дописывались слоями `@media (min-width: 1200px)` после
  мобильных правил, а не проектировались как компоненты;
- сверка шла «сверху вниз»: сначала высота секции, потом подгонка элементов.
  В результате секция совпадала по высоте, а кнопка внутри была на 53 px уже
  макетной;
- иконки, плеер, шевроны и часть картинок собирались руками, потому что
  Figma API упирался в квоту, а локальный `.fig` не использовался на полную;
- контент переносился копипастом, поэтому цены, длительности, количество
  карточек и даже фото в карточках разошлись с макетом;
- полноценная визуальная сверка была только у одной страницы из одиннадцати.

Что нужно сохранить:

- локальный разбор `.fig` — это главный актив проекта;
- культуру числовой и визуальной проверки, `BLOCKED` как честный статус;
- принцип «переносим, а не придумываем»;
- документацию, журнал проблем макета, git-дисциплину;
- локальные шрифты и полный отказ от внешних запросов.

Предлагаемый вектор: **Figma → спецификация → компоненты → страницы →
автоматическая сверка**. Не «сначала HTML, потом подгонка», а «сначала
компонент, доказанно совпавший с макетом, потом сборка страницы из него».

### 2.4 Главное ограничение

Figma REST API и MCP сейчас отвечают `429` с `retry-after` около 4,5 суток
(место Viewer/Collaborator). Строить процесс вокруг API нельзя. Но локальный
`.fig` содержит практически всё, что нужно:

- дерево с `stackMode`, `stackSpacing`, `stackPadding`, выравниванием и
  размерами;
- тексты, шрифты, кегли, `lineHeightPx`, трекинг, `textAutoResize`;
- заливки, обводки, радиусы, эффекты;
- `fillGeometry`/`strokeGeometry` — из них можно собрать SVG без API;
- `imageRef` и исходные изображения;
- компоненты, варианты, инстансы и переопределения.

Не хватает только **рендеров страниц в PNG**. Это решается одним экспортом
из Figma (7 файлов) или одним пакетным запросом к API, когда квота оживёт.
Полное дерево и SVG — не требуют API.

## 4. Что сломалось и не повторяется

### 4.1 Дубли разметки вместо компонентов

11 копий шапки и 11 копий подвала. Разметка отличается, потому что
активные пункты и вариант шапки прописаны вручную. В новом проекте это
`<SiteHeader active="practice" theme="dark" shape="floating" />` и
`<SiteFooter />` — один источник.

### 4.2 Страничный CSS как слой заплаток

`practice.css` — 1 042 строки, 27 блоков `min-width: 1200px`. Это не
mobile-first и не дизайн-система, а накопленные исключения. В новом проекте:
токены → базовый слой → компонентные стили (scoped) → страница только
композиция. Никаких «допишу ещё один media query в конец».

### 4.3 Сверка по высотам, а не по компонентам

Секция «Платные практики» сошлась по высоте, но кнопка внутри была на
53 px уже. Причина: проверяли контейнер, а не компонент. В новом проекте
сначала доказывается компонент (кроп из рендера Figma против кропа
компонента), потом страница.

### 4.4 Ручной перенос контента

Цены, длительности, состав пакетов и фото переносились глазами. Отсюда:

- 52 минуты во всех карточках макета против 47/49/43/40/36 на сайте;
- цены пакетов 160/240/360 в макете против 189/189/299 на сайте;
- 8-я карточка «Кодов» — дубль другой практики;
- в первой бесплатной карточке стоит не то фото.

В новом проекте контент извлекается из узлов и проходит `content-diff`
против старого сайта и решений владельца. Расхождения не «чинятся» молча.

### 4.5 Иконки и плеер руками

Play, стрелки, шеврон, часы, волна — часть нарисована CSS/приблизительно,
потому что API не отдавал SVG. Пользователь это заметил. В новом проекте
вектор берётся из `fillGeometry`/`strokeGeometry` локального `.fig`
(или из SVG-экспорта, когда API доступен). Если геометрия не полная —
фиксируем как исключение, а не рисуем «похоже».

### 4.6 Якоря вручную и только на одной странице

40 `data-figma-node` на весь сайт, 125 якорей только на «Практиках».
Остальные страницы принимались по высотам секций. В новом проекте
`data-figma-id` стоит на каждом компоненте и ключевой части, а карта
строится из спецификации, а не по тексту.

### 4.7 Один визуальный эталон на 11 страниц

PNG есть только для `practice`. Остальное — числа. В новом проекте
7 рендеров страниц обязательны до приёмки; без них статус `BLOCKED`.

### 4.8 API в критическом пути

Квота закончилась в середине работы: SVG не выгрузились, рендеры не снялись.
В новом проекте API — необязательный ускоритель. Критический путь: `.fig` +
ручной экспорт PNG + локальные шрифты.

### 4.9 Неразрешённые инстансы и дубли фреймов

В файле есть дубли (`voices` — 11 копий, `formats` — 4, `faq` — 4,
`founder-hero` — 4, `quiz` — 2). Часть текстовых стилей в инстансах
переопределена. В сессии это проявилось как «в разборе Golos 20, а в рендере
Literata»; проверка узла `427:1249` показывает Literata Light 29. То есть
проблема скорее в выборе не того узла/инстанса, чем в самом файле. Нужны:

- реестр канонических фреймов;
- резолюция инстансов и override-ов до чтения стилей;
- кросс-проверка шрифта по рендеру.

### 4.10 Мобильной вёрстки нет в макете

Все фреймы 1440. Старая адаптация — инженерная импровизация. В новом проекте
её нельзя выдавать за перенос дизайна. Нужно либо получить мобильные фреймы,
либо явно вынести адаптив в отдельный слой с отдельными критериями.

## 5. Принципы нового проекта

1. **Figma — источник структуры и контента, но не истина в бизнес-фактах.**
   Цены, длительности, имена, юридические тексты подтверждает владелец.
2. **Компонент — единица верности.** Страница не принимается, пока её
   компоненты не совпали с макетом.
3. **Спецификация — оракул.** Проверка идёт не «на глаз» и не по тексту, а
   по узлам с `id`, координатами и стилями.
4. **Полнота важнее среднего.** Каждый видимый узел либо отображён, либо
   явно исключён. «В среднем похоже» не считается.
5. **Контент — данные, а не разметка.** Тексты, карточки, форматы, вопросы —
   в типизированных данных; страница — композиция.
6. **Локально и статично.** Никаких внешних шрифтов, CDN и аналитики.
   Runtime — статический HTML/CSS/JS.
7. **Одна страница за раз, три цикла исправлений.** После трёх — стоп и
   список остаточных расхождений.
8. **Никаких «улучшений» по пути.** Нет в макете — нет на сайте; нет
   состояния — не рисуем; нет мобильного фрейма — не называем это дизайном.

## 6. Архитектура

### 6.1 Стек: развилка

**Решение 04.11.2026:** Payload/CMS откладываем — пока нет готовности к БД,
админке и эксплуатации. Рассматриваем три варианта: Astro, Eleventy и чистый
HTML/CSS. Payload остаётся вариантом на будущее, если появится регулярная
редактура и серверные функции.

Стек зависит не от вкуса, а от двух вопросов:

1. Кто и как часто будет менять контент после запуска — разработчик или
   владелец/клиент?
2. Нужны ли серверные функции: реальные заявки, запись, аккаунты, оплата,
   аудио-библиотека?

Если ответы «редко / разработчик» и «нет» — достаточно статического сайта.
Если «владелец / регулярно» или «да» — позже появляется смысл в CMS. Но это
не блокирует вёрстку: контентный слой можно сразу отделить от разметки.

#### Сначала: почему не чистый HTML/CSS

Чистый HTML/CSS — хороший выбор для 3–5 страниц, которые делает один человек
и которые редко меняются. У нас другая ситуация:

- 11 страниц, шапка и подвал в 11 копиях (в старом проекте — 7–8 разных
  вариантов разметки);
- 18 компонентных наборов и варианты кнопок/карточек;
- 92 изображения, 14 шрифтов, 4 000 строк CSS;
- жёсткое требование совпадения с макетом, а значит — повторяемые
  компоненты, а не «ещё одна копия карточки».

Без слоя шаблонов мы снова получим 11 копий шапки и CSS-заплатки. Нам нужен
не фреймворк в браузере, а **шаблонизатор/генератор статических страниц**:
один раз описать шапку, подвал, кнопку и карточку, а страницы собрать из них.

#### Astro — это не runtime

Astro — генератор статических сайтов. В браузер не попадают ни Astro, ни
React, если не добавлять интерактивные острова. На выходе — обычные
`index.html`, `method.html`, `assets/*.css`, `assets/*.js`.

Компонент выглядит почти как HTML с props:

```astro
---
// src/components/SiteHeader.astro
const { active = '' } = Astro.props;
---
<header class="site-header">
  <a href="/" class="logo">Syntonia</a>
  <nav aria-label="Основная навигация">...</nav>
</header>

<style>
  .site-header { display: flex; gap: 24px; }
</style>
```

Страница — тоже HTML:

```astro
---
import SiteHeader from '../components/SiteHeader.astro';
---
<html lang="ru">
  <body>
    <SiteHeader active="practice" />
    <main>...</main>
  </body>
</html>
```

`<style>` в Astro по умолчанию scoped: классы не текут на другие компоненты.
Это лечит главную болезнь старого проекта — глобальный CSS, который
приходилось переопределять 27 блоками `@media`.

Что такое «сборка»: `npm run dev` — локальный сервер с hot reload;
`npm run build` — один раз собирает `dist/` со статикой. Astro лежит в
`devDependencies`, в браузер не попадает. Сайт остаётся статическим, как и
раньше; сборка нужна разработчику, а не посетителю.

#### Вариант A — Astro static

Плюсы:

- компоненты и layouts без ручного дублирования шапки/подвала;
- scoped CSS и нормальная работа с токенами;
- штатная оптимизация изображений (`astro:assets`, sharp, WebP/AVIF,
  `srcset`, размеры);
- zero-JS по умолчанию; интерактив — маленькие TS-модули;
- на выходе обычный статический сайт, который можно положить на любой хостинг;
- нет БД, авторизации, бэкапов и обновлений сервера;
- Playwright и npm-инструменты уже знакомы по старому проекту.

Минусы:

- нет админки: контент правится в коде/JSON;
- формы — через внешний сервис или serverless-функцию;
- аккаунты/оплата/аудио-библиотека — отдельный проект;
- если CMS понадобится, её придётся добавить отдельным приложением.

Сохраняем старые адреса (`/method.html`, `/practice.html`): в Astro это
`build.format: 'file'` либо редиректы. Внешние ссылки и закладки не ломаем.

#### Вариант B — Next.js + Payload

Один React-приложение: публичная часть на Next.js App Router, админка и API —
Payload (Next-native версия) внутри того же приложения.

Что даёт:

- админка, коллекции, глобалы, drafts/versions, live preview, роли;
- локальный Payload API прямо в server components — без HTTP-прослойки;
- хранение заявок/записей, формы, медиатека, alt-тексты;
- естественная база для аккаунтов, платных практик и аудио-библиотеки;
- React-компоненты и один деплой на всё;
- ISR/`revalidatePath` по хуку публикации: контент обновляется без ручной
  сборки.

Что стоит:

- нужна БД (Postgres/Mongo), миграции, бэкапы, мониторинг;
- нужен Node-runtime: `output: 'export'` с Payload несовместим, то есть
  это Vercel/VPS/Docker, а не «просто статический хостинг»;
- файлы — S3/R2 или диск VPS; на serverless локальный диск не подходит;
- авторизация, безопасность, обновления зависимостей, восстановление из
  бэкапа — теперь часть проекта;
- +1–2 недели на CMS/ops по сравнению с Astro;
- CMS может разрушить вёрстку, если дать редактору свободный page builder.
  Нужны фиксированные схемы и варианты блоков, а не «любая секция из ничего».

Дизайн-фиделити это не ухудшает: те же токены, CSS Modules, те же кропы и
Playwright. Но `next/image` и `next/font` нужно настраивать аккуратно, чтобы
не появились другие кропы и метрики.

#### Вариант C — Astro + Payload headless

Публичный сайт остаётся статическим Astro, Payload живёт отдельно
(`cms.domain.com`) и отдаёт контент по REST/GraphQL. Публикация запускает
build hook, сайт пересобирается.

Плюсы:

- быстрый и дешёвый публичный сайт на CDN;
- админка есть;
- можно сохранить статический хостинг.

Минусы:

- два приложения и два деплоя;
- обновление контента = пересборка (минуты, не секунды);
- preview черновиков сложнее;
- всё равно нужны БД, бэкапы и сервер для CMS.

#### Сравнение

| Критерий | Astro static | Next + Payload | Astro + Payload |
|---|---|---|---|
| Скорость первой страницы | высокая | средняя | высокая |
| Админка/CMS | нет | да | да |
| Реальные заявки | сервис/функция | встроенное хранение | сервис или API Payload |
| Аккаунты/оплата/аудио | отдельный проект | естественное продолжение | возможно, но сложнее |
| Хостинг | статика/CDN | Node/Vercel/VPS | статика + CMS |
| БД и бэкапы | нет | да | да |
| Ops-нагрузка | низкая | средне-высокая | средняя |
| Дизайн-фиделити | высокая | высокая | высокая |
| React-навыки | не нужны | нужны | опционально |
| Время до первой страницы | 1–2 недели | 3–4 недели | 3–4 недели |
| Стоимость | низкая | средняя | средняя |
| Лучше всего для | витрины | платформы | статики + CMS |

#### Что рекомендую

- **Если CMS и серверные функции не подтверждены** — Astro static. Это самый
  короткий путь к доказанной вёрстке и самый дешёвый в эксплуатации.
- **Если владелец будет регулярно править контент, а заявки/аккаунты/оплата
  реально в ближайших планах** — Next.js + Payload. Это цельная платформа,
  и React здесь уместен, а не «лишний runtime».
- **Если нужен именно статический хостинг, но CMS нужна** — Astro + Payload
  headless.
- **Если главная цель — освоить React/Next**, это законный мотив, но тогда
  CMS и ops нужно считать частью проекта, а не бесплатным бонусом.

Ключевое: пайплайн Figma → spec → компоненты → проверки **не зависит от
стека**. Меняются синтаксис компонентов и способ доставки контента, а не
метод доказательства соответствия макету.

### 6.4 Layout-примитивы

Figma auto-layout переносится в CSS предсказуемо:

| Figma | CSS |
|---|---|
| `stackMode: HORIZONTAL/VERTICAL` | `flex-direction: row/column` |
| `stackSpacing` | `gap` |
| `stackHorizontalPadding` / `VerticalPadding` | `padding` |
| `stackPrimaryAlignItems` | `justify-content` |
| `stackCounterAlignItems` | `align-items` |
| `stackPrimarySizing` | `width`/`height`: fixed, hug, fill |
| `stackChildPrimaryGrow` | `flex-grow` |
| `stackPositioning: ABSOLUTE` | `position: absolute` |
| `clipsContent` | `overflow: hidden` |
| `textAutoResize` | `white-space`, `width`, `max-lines` |

Не нужно писать «универсальный движок Figma». Достаточно 5–7 примитивов
(`Stack`, `Cluster`, `Grid`, `Container`, `Section`) и явных компонентных
стилей. Спецификация остаётся проверочной, а не генерирует div-суп.

### 6.5 Токены

Источник — не страница «Design system» (она устарела), а фактические
значения компонентов и страниц:

- цвета: сгруппировать по роли (`bg-page`, `text-heading`, `accent`,
  `border`, `on-image`) и сверить с переменными Figma;
- типографика: семейство + начертание + кегль + `lineHeightPx` +
  `letterSpacing`; сгруппировать в роли, а не в 15 случайных размеров;
- отступы: 4/8/12/16/24/32/40/64/96 из стеков;
- радиусы, тени, обводки, прозрачности;
- исключения (`one-off`) документируются, а не прячутся в токен.

Правило: в компонентах только `var(--token)`. Если значение встречается
один раз, это локальная константа компонента с комментарием.

### 6.6 Шрифты

В макете фактически используются:

- Golos Text Regular/Medium;
- Literata Light/Regular;
- Lora Italic/Medium;
- Great Vibes;
- Lovers Quarrel;
- Cormorant Garamond Light;
- Hurricane;
- Inter (в небольшом числе узлов; проверить после выбора канонических фреймов).

В старом проекте нет Lovers Quarrel, Hurricane и Inter, зато есть Marck
Script, которого в макете нет. Это прямая причина расхождений подписей.

План:

1. Инвентаризация только по каноническим страницам.
2. Скачать woff2 (все семейства — Google Fonts, OFL), проверить лицензии.
3. Подмножества `cyrillic` + `latin`, `unicode-range`, `font-display: swap`.
4. Кегль и `line-height` — в px из `lineHeightPx`, а не unitless.
5. Проверить, что браузер не синтезирует жирный/курсив.
6. Сверить метрики через fontTools и кроп текста в рендере.

### 6.7 Изображения и вектор

Для каждого image-узла:

- исходник из `design/figma/images/` по `imageRef`;
- абсолютный бокс, `scaleMode`, `imageTransform`, оригинальные размеры;
- кроп/ресайз в 1x и 2x, WebP + JPEG fallback;
- `width`/`height`, `srcset`, `loading` (hero — eager, остальное lazy);
- `alt` из Figma или осмысленный вручную;
- округления — через CSS `border-radius`/`mask`, если это маска, а не
  запечённый кроп.

Для вектора:

- декодировать `commandsBlob` из `fillGeometry`/`strokeGeometry` в SVG path;
- сохранить заливки, обводки, градиенты, `fill-rule`;
- иконки — в SVG-спрайт/компонент `Icon`;
- если геометрия неполная — пометить исключение и запросить SVG из Figma,
  но не рисовать приблизительно.

### 6.8 Контент

- Извлечь все текстовые узлы страницы с `id`, `characters`, стилем,
  координатами.
- Собрать `design/spec/<page>.json` и человекочитаемый `<page>.md`.
- Нормализовать только по согласованию: двойные пробелы, мягкие переносы,
  неразрывные пробелы.
- Сравнить с `data/*.js` старого сайта: цены, длительности, состав, имена,
  количество карточек, фото.
- Все расхождения — в `design/decisions/CONTENT.md` с датой и решением.
- Незакрытое — `data-draft`, не публиковать.

### 6.9 Интерактив

Маленькие TS-модули на компонент:

- меню и dropdown;
- FAQ-аккордеон;
- слайдер отзывов/библиотеки;
- тест: вопросы из макета (в файле виден только экран «Вопрос 1 из 9»;
  полный набор — открытый вопрос, см. риски);

- валидация формы без имитации отправки;
- аудио, оплата и отправка заявок не имитируются: если интеграции нет,

- `prefers-reduced-motion`.

Без глобального `script.js` на 27 КБ и без фреймворка.

### 6.10 Адаптив

Макета нет. Предлагаю:

- 1440 — точная сверка, приёмка;
- 1200/768/390 — инженерный адаптив: переполнение, читаемость, тап-таргеты,

- адаптив не выдаётся за перенос дизайна;
- если заказчик даст мобильные фреймы — они становятся отдельным этапом
  с такой же сверкой.

## 7. Пайплайн Figma → сайт

```
.fig
  │ extract
  ▼
resolved tree (инстансы, overrides, канонические фреймы)
  │
  ├── spec/<page>.json ──────────────┐
  ├── assets (images, SVG, fonts)    │
  └── content (тексты, данные)       │
                                     ▼
                              components + pages
                                     │
render PNG ── verify geometry ── verify pixel ── verify a11y ── review
```

### Этап 1. Ingestion

`tools/figma-extract.mjs`:

- полный разбор `.fig` без потери `stack*`, `text*`, `effects`, `geometry`;
- `raw/` для отладки, `pages/` для работы;
- манифест версии: file key, version, lastModified, SHA256 `.fig`;
- проверка: 2 701 узел, 128 изображений, 18 наборов, 92 символа.

### Этап 2. Resolution

- канонический фрейм каждой страницы (`canonical.json`);
- дубли и «вторые» фреймы — в `ignored`;
- применение `symbolOverrides`, `derivedSymbolData`, `componentPropAssignments`;
- резолюция переменных и текстовых стилей;
- абсолютные координаты и размеры;
- отчёт о подозрительных шрифтах/размерах (сверить с рендером).

### Этап 3. Spec

`design/spec/<page>.json`:

- секции с `figmaId`, боксами, компонентом, вариантом;
- инстансы с пропсами (текст, картинка, цена, длительность);
- текстовые узлы с полным стилем;
- image/vector-узлы с ассетом;
- флаги `required` / `decorative` / `ignored`.

Это одновременно:

- ТЗ для вёрстки;
- фикстура для тестов;
- документ для ревью с заказчиком.

### Этап 4. Assets

- изображения и кропы;
- SVG из геометрии;
- шрифты;
- манифест `ASSETS.md` с источником, лицензией, alt.

### Этап 5. Content

- `content-diff` Figma ↔ старый сайт ↔ решения владельца;
- `DECISIONS.md` по ценам, длительностям, составу, именам, тесту;
- типизированные данные в `src/data`.

### Этап 6. Build

- компоненты;
- страницы-композиции;
- интерактив;
- сборка `dist/`.

### Этап 7. Verify

Четыре уровня:

1. **Полнота.** Каждый видимый узел спецификации отображён или исключён.
   Отчёт: `mapped / ignored / missing`.
2. **Геометрия.** DOM-элементы с `data-figma-id` против боксов:
   `|Δx|, |Δy|, |Δw|, |Δh| ≤ 1 px` (цель 0,5 px), плюс семейство, кегль,
   `line-height`, трекинг, число строк.
3. **Компонентный кроп.** Кроп рендера Figma и кроп скриншота по боксу
   инстанса; доля расхождения, тепловая карта. Это ловит кнопку 196×34
   внутри секции, которая сошлась по высоте.
4. **Страница.** Полный скриншот 1440 против рендера; UI-слой без фото,
   допуск ≤ 1 % (цель ≤ 0,5 %), без кластеров > 4 px.

Плюс:

- 390/768/1440: нет горизонтального переполнения, ошибок консоли, битых
  ассетов;
- шрифты загружены, `document.fonts.ready`;
- axe: 0 serious/critical;
- клавиатура и `focus-visible`;
- ручное бок-о-бок ревью.

### Рендеры: как получить

Нужны 7 PNG (по одной на дизайнерскую страницу), 1440 px, лучше 2x:

- Home `79:103` — 1440 × 10 548;
- Method `323:422` — 1440 × 2 737;
- Masters `217:237` — 1440 × 3 886;
- Practice `408:241` — 1440 × 9 291;
- Library `267:450` — 1440 × 3 188;
- Quiz `529:118` — 1440 × 1 218;
- Booking `383:286` — 1440 × 2 416.

Способы по убыванию надёжности:

1. Ручной экспорт из Figma (не тратит API).
2. Один пакетный запрос `/v1/images?ids=...` когда квота оживёт.
3. MCP `download_figma_images` (та же квота).
4. Локальный рендер `.fig` — только как отладочный, не как эталон.

Без рендеров геометрию и полноту проверить можно, пиксельную приёмку — нет.
Статус `BLOCKED` честнее, чем «совпало».

## 11. Решения, которые нужны до старта

1. **Кто редактирует контент.** Разработчик / владелец или клиент / оба.
   Как часто: разово, раз в месяц, регулярные выпуски.
2. **Серверные функции.** Нужны ли реальные заявки и запись с хранением в
   админке, аккаунты, оплата, аудио-библиотека — сейчас или в ближайшие
   6–12 месяцев.
3. **Стек (сейчас).**
   - Astro + обычный CSS + vanilla TS — рекомендуемый вариант;
   - Eleventy + Nunjucks + обычный CSS — если нужен максимально «HTML-first»
     и минимум магии;
   - чистый HTML/CSS — только если готовы к 11 копиям шапки и ручным

   Payload/Next — отложены, не сейчас.
4. **Хостинг.** Статический хостинг/CDN; БД и серверная часть сейчас не

## 12. Что дальше

Пока стек не выбран, можно начинать только со stack-agnostic части:

1. заново выгрузить `.fig` и зафиксировать версию;
2. собрать расширенный экстрактор и канонические фреймы;
3. импортировать 7 рендеров;
4. собрать токены, шрифты, ассеты;
5. описать компонентную карту и spec.

После выбора стека — фаза 0:

1. создать `syntonia-v2`, git, каркас (Astro или Eleventy);
2. сделать `SiteHeader`, `SiteFooter`, `Button`, `Icon`, `SectionHead` и
   доказать их кропами;
3. показать первый отчёт: что совпало, что `BLOCKED`, какие решения нужны.

Критерий первого этапа: не «страница выглядит похоже», а «есть компоненты,
кропы и числа, по которым видно, что именно совпало».
