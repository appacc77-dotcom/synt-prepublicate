# Процесс: сайт по макету Figma

Версия 0.1 · 04.11.2026 · Syntonia как первый прогон

Документ описывает не «как верстать», а **как получить предсказуемый результат из
файла, который никто не готовил к автоматическому переносу**. Он не привязан к
Syntonia: входы — `.fig` и экспорт канваса, выходы — сайт и отчёт.

---

## 1. Зачем этот процесс

Три проблемы, которые он решает, все наблюдались на первом прогоне:

| Проблема | Как выглядела | Чем лечится |
|---|---|---|
| Ошибка находится поздно | Кнопка 196×34 против 249×45 обнаружилась на 60-м ходу, после того как страница «сошлась по высоте» | Приёмка на компоненте, до сборки страниц |
| Работа не накапливается | 11 копий шапки, 6 вариантов разметки, 4501 строка CSS | Компонент как единственная единица существования элемента |
| Неоднозначность файла становится блокером | В конце: «нужны PNG шести страниц», «решите цены» | Проверка реальности файла в самом начале + журнал решений |

Процесс считается работающим, если **новый человек или агент, начав с нуля,
приходит к тому же результату теми же командами**.

## 2. Принципы

1. **Единица работы — компонент. Страница — композиция.** Не наоборот.
2. **Единица приёмки — тоже компонент.** Страница принимается только из принятых
   компонентов.
3. **Переносим то, что нарисовано.** Не улучшаем, не додумываем, не
   «оптимизируем» дизайн.
4. **Генерируем, а не переписываем.** Токены, типографика, состав компонентов —
   из файла. Руками набранное значение считается дефектом.
5. **Компонент не знает, где он стоит.** Ни `width`, ни `margin` на месте
   вызова. Если размер не сошёлся — виноват шрифт, трекинг или паддинг.
6. **Любая неоднозначность файла решается до вёрстки** и записывается в журнал
   решений с датой и автором.
7. **Проверка — команда с числом и кодом возврата.** «Посмотрел глазами» — не
   проверка, а впечатление.
8. **У каждого документа две версии.** Человеческая — смысл, варианты,
   последствия, без имён полей и id. Агентская — контракты, признаки в данных,
   команды, пороги. Один документ на две аудитории не работает: человек тонет в
   `stackPositioning`, агент тонет в «примерно так».

### 2.1 Два языка

| | Человеческая версия | Агентская версия |
|---|---|---|
| Кому | владелец, дизайнер, заказчик | агент, разработчик |
| Файл | `*.md` | `*.agent.md` |
| Содержит | что случилось, что это значит, какие варианты, что рекомендуем | id узлов, поля, было → стало, команды, пороги |
| Не содержит | `stackPositioning`, `uniformScaleFactor`, id вида `410:1182` | рассуждений «мне кажется» |
| Проверка | человек прочитал и понял, что делать | агент выполнил команду и получил тот же результат |

Признак дефекта: если в человеческом документе встретилось имя поля из Figma —
документ переписывается. Если в агентском нет команды, которой это проверяется, —
знание не закреплено.

## 3. Артефакты

| Артефакт | Кто создаёт | Когда | Зачем |
|---|---|---|---|
| `extracted/` — разбор `.fig` | `figma-extract` | P0 | единственный источник геометрии |
| `reports/reality.md` | `figma-reality` | P1 | что в файле на самом деле |
| `docs/decisions.md` | человек + агент | P1 → P2 | каждое «непонятно» с решением |
| `spec/<page>.json` | `figma-resolve` | P2 | канонические секции, компоненты, боксы |
| `tokens.css`, `typography.css` | `figma-tokens` | P3 | значения из переменных и стилей |
| `inventory.md` | `figma-inventory` | P3 | 1:1 соответствие набор Figma ↔ файл |
| `crops/<component>.png` | `figma-crops` | P3 | эталон для приёмки компонента |
| `src/components/ds/*` | агент | P4 | библиотека |
| `/ds` — живой справочник | агент | P4 | одна страница со всеми вариантами |
| `reports/ds-gate.md` | `ds-check` | G1 | числа по каждому компоненту |
| `reports/pages-gate.md` | `page-check` | G2 | числа по каждой странице |
| `changes.md` / `changes.agent.md` | `figma-diff` | после новой выгрузки | что изменилось в макете |
| `problems.md` / `problems.agent.md` | агент | P1 → P2 | проблемы файла и варианты решений |
| `docs/tutorial.md` | агент | постоянно | учебник: что и зачем делали |
| `docs/architecture.md` | агент | один раз | как устроено решение |

## 4. Фазы

```
P0 Ingest      .fig ──────────────► extracted/*.json
P1 Reality     extracted ─────────► reports/reality.md + decisions.md   [G0]
P2 Resolve     extracted + decisions ► spec/*.json
P3 Model       extracted ─────────► tokens.css, typography.css, inventory, crops
P4 Components  spec + model ──────► ds/*.astro + /ds                   [G1]
P5 Pages       components ────────► страницы                           [G2]
P6 Adaptive    страницы ──────────► 390/768                            [G3]
P7 Accept      всё ───────────────► отчёт, передача
```

### P0. Ingest

Один раз на версию файла. Локальный `.fig` предпочтительнее API: API отдаёт
снимок на момент запроса, квота кончается, и в критический путь он попадать не
должен. Фиксируем хеш файла в `extracted/manifest.json` — иначе непонятно, к
какой версии относятся отчёты.

### P1. Reality check

Самая дешёвая и самая недооценённая фаза. Одна команда, двадцать секунд,
и на столе список того, что в файле не так:

- сколько фреймов, какие ширины, есть ли адаптив;
- сколько инстансов отмасштабировано и какие;
- сколько инстансов с override;
- сколько дублей фреймов и какие считаем каноническими;
- покрытие auto-layout;
- какие наборы компонентов есть и где используются.

Результат — **журнал решений**. Пока в нём есть открытые красные пункты, дальше
идти нельзя: именно они всплывают в конце и стоят дороже всего.

### P2. Resolve

`extracted` — это дерево, а не проект. Resolve делает из него однозначный
документ:

- выбирает канонический фрейм страницы (`main`), остальные помечает как варианты;
- применяет override-ы инстансов;
- применяет (или явно игнорирует) `uniformScaleFactor`;
- подставляет значения переменных вместо id;
- нормализует текст (пробелы, переносы, ё);
- раскладывает абсолютные координаты относительно секции;
- пишет `spec/<page>.json`: секции → компоненты → боксы → тексты → ассеты → флаги.

Spec — одновременно ТЗ, фикстура для тестов и документ для ревью. Он не
содержит «решений», только факты и ссылки на решения.

### P3. Model

Из файла генерируются:

- `tokens.css` — цвета, отступы, радиусы, контейнер (из `variables.json`);
- `typography.css` — стили текста (из `styles.json`), с размерами и трекингом;
- `inventory.md` — таблица «набор Figma → файл компонента → где используется»;
- `crops/` — по одному эталонному изображению на компонент, вырезанному из
  экспорта канваса по bounds.

### P4. Components и ворота G1

Пишем компоненты **по одному**, в порядке «сначала те, что встречаются чаще».
Каждый сразу попадает в `/ds` — страницу, где отрисованы все варианты в
масштабе 1:1. `ds-check` сравнивает `/ds` с `crops/` и печатает таблицу.

Смысл ворот: если кнопка неверна, она неверна в одном месте. Если верна — верна
в сорока.

### P5. Pages и ворота G2

Страница собирается из компонентов и данных. Своих стилей у страницы почти нет:
только раскладка секций и порядок.

### P6. Adaptive

Отдельный трек с отдельными критериями, потому что мобильных фреймов обычно нет.
Либо дизайнер их рисует, либо это инженерный слой — и тогда он никогда не
называется «по макету».

### P7. Accept

Отчёт: что проверено, какими командами, какие числа, что осталось и почему.

## 5. Ворота

| Ворота | После | Проверка | Порог | Кто закрывает |
|---|---|---|---|---|
| **G0** | P1 | `decisions.md` | 0 открытых 🔴 | владелец |
| **G1** | P4 | `ds-check` | 100% наборов; геометрия 100% в ±1 px; стиль 100% (шрифт, кегль, трекинг, цвет, заливка, обводка); 0 override на месте вызова | агент + ревью |
| **G2** | P5 | `page-check` | якоря 100% в ±1 px; пиксель ≤ 0,5%; высоты секций Δ0; 0 самодельных примитивов | агент + ревью |
| **G3** | P6 | `adaptive-check` | нет переполнения 390/768/1440; тап-таргет ≥ 44 px; контраст ≥ 4,5 | агент |

**Про пиксельный порог.** Первая версия ворот требовала кроп-дифф ≤ 0,5%. Замеры показали,
что это недостижимо и бессмысленно: при совпадающих шрифте, кегле, позиции и цвете Figma и
браузер растеризуют глифы по-разному, и в текстовой области расходится 11–12% пикселей.
Фон, заливка, скругления и текстура при этом совпадают до 0,2%. Поэтому ворота закрываются
по геометрии и стилю — это точные, проверяемые величины, — а пиксельное сравнение остаётся
сигналом регрессии: если число выросло вдвое, что-то поехало.

Ворота — не бюрократия, а точка, где дешевле остановиться, чем продолжать.
G1 проходится за день и экономит неделю.

## 6. Definition of Done

### Компонент

- [ ] имя файла = имя набора в Figma (`btn-primary.astro` ↔ `btn-primary`);
- [ ] API = пропсы Figma (`theme`, `size`, `caps`, `arrow`), без выдуманных;
- [ ] ни одного `width`/`margin`, зависящего от места вызова;
- [ ] размеры и цвета только из сгенерированных токенов;
- [ ] есть в `/ds` во всех вариантах;
- [ ] геометрия: размер совпадает с вариантом в макете в пределах 1 px;
- [ ] стиль: шрифт, кегль, интерлиньяж, трекинг, цвет текста, заливка, обводка, радиус;
- [ ] пиксельное расхождение записано (сигнал регрессии, не критерий).

### Страница

- [ ] собрана только из `ds/*` и данных;
- [ ] высоты секций = spec (Δ0);
- [ ] якоря 100% в ±1 px;
- [ ] пиксель записан и не вырос против прошлого прогона (сигнал регрессии);
- [ ] нет переполнения на 390/768/1440;
- [ ] сборка зелёная, консоль пустая;
- [ ] `data-figma-node` на каждой секции — трассировка к макету.

## 7. Каталог ситуаций «файл врёт»

Это главная переиспользуемая часть. Каждая строка — то, что уже встречалось.

| # | Ситуация | Признак в данных | Решение | Кто |
|---|---|---|---|---|
| 1 | Инстанс отмасштабирован | `instance.uniformScaleFactor ≠ 1` | не воспроизводить дробный масштаб; нормализовать к ближайшему варианту/токену, отклонение записать | дизайнер + агент |
| 2 | Инстанс переопределён | `overrideCount > 0` | применить override; если их больше 30% у компонента — сигнал, что вариант не тот | агент |
| 3 | Дубли фреймов | одинаковые имя+размер на канвасе | канонический — `main`, остальные — матрица вариантов; выбор записать | агент |
| 4 | Нет адаптива | нет фреймов уже 1440 | мобилка — отдельный трек, не «перенос» | владелец |
| 5 | Кегль в узле не соответствует отрисовке | `fontSize` × строки ≠ высоте узла | верить высоте узла и числу строк, не `lineHeightPx` | агент |
| 6 | Изображение отсутствует в файле | `imageRef` без записи в `images/` | заявка на экспорт, блокирует только этот компонент | владелец |
| 7 | Переносы внутри текста | `\n` в `characters` | нормализовать, если не задумано | агент |
| 8 | Одинаковые секции разного размера | сравнение заголовков по имени | считать дефектом файла, брать вариант с канонической страницы | дизайнер |
| 9 | Компонент в библиотеке устарел | размер варианта ≠ размеру инстанса | инстанс важнее библиотеки; библиотеку чинить отдельно | дизайнер |
| 10 | Текст есть в макете, но не на странице | разница `texts.json` и spec | не додумывать: либо в макет, либо в решение | владелец |

## 8. Управление

**Канбан.** Карточка = компонент или секция. В карточке — критерии приёмки и
команда проверки. Карточка не переходит в «Готово» без зелёной команды.

**Журнал решений.** `docs/decisions.md`, формат: вопрос → варианты → решение →
кто → когда → чем проверено. Один раз решённое не обсуждается заново.

**Стоп-линия.** Не пройден G1 — страницы не начинаются. Не закрыт G0 — не
начинается P4.

**Правило одного экрана.** Первая страница — калибровка. Пока она не прошла G2,
остальные не начинаются: на ней проверяется весь конвейер.

**Правило снимка.** Любое число в отчёте относится к хешу `.fig`. Без хеша
отчёт — воспоминание.

## 9. Перенос на новый сайт

1. Положить `.fig` в `design/figma/`, выгрузить канвас страниц и канвас
   дизайн-системы в PNG 1:1.
2. `figma-extract` → `extracted/`.
3. `figma-reality` → `reports/reality.md`. Прочитать целиком.
4. Заполнить `decisions.md` по красным пунктам, получить решения владельца.
5. `figma-tokens` + `figma-inventory` + `figma-crops`.
6. Собрать `/ds`, прогнать `ds-check`, закрыть G1.
7. Калибровочная страница, закрыть G2.
8. Остальные страницы пачкой.

Шаги 1–5 — это часы. Шаги 6–7 — дни. Шаг 8 — самый предсказуемый.

## 10. Метрики процесса

Их стоит считать, иначе непонятно, становится ли лучше:

- компонентов до G1 и число правок на компонент;
- доля страниц без override на месте вызова;
- время от P0 до G1 и от G1 до G2;
- число пунктов в `decisions.md`, открытых дольше недели;
- сколько раз пришлось вернуться на предыдущую фазу.
