# Агентная система разработки сайта

Версия 0.1 · 04.11.2026

Система надстраивается над [PROCESS.md](PROCESS.md) (фазы P0–P7,
ворота G0–G3) и над тем, что уже сделано в `syntonia-v2`. Первый агент —
**верстальщик**. Здесь — кто ещё нужен, что между ними происходит и как это
запускать в DSH.

## 1. Что показали соседние сессии

| Сессия | Объём | Чем закончилась |
|---|---|---|
| `syntonia-deepseek` (исторический проект) | 88 ходов, 1604 вызова, ~8,5 ч | цель заблокирована на 40-м раунде: нет PNG, нет решений по ценам |
| `syntonia-v2` (вне проекта) | ~2 ч, 12 компонентов | 9 из 15 секций главной; дрейф уже начался |
| обсуждение процесса | — | [PROCESS.md](PROCESS.md), `figma-layout-kit`, канбан |

Четыре числа объясняют остальное:

- **249×44,7 в дереве — 182,6×32,7 на холсте.** Кнопку на карточке практики дизайнер
  сжал до 73,24%: дерево отдало размер символа, холст — умноженный на масштаб.
  Старый сайт рисовал её 196×34, то есть реальное расхождение было 14×1 px, а не
  53×11. Инструмент сверки требовал размер, которого на картинке нет, и «дойти до
  нуля» по нему было невозможно по определению.
- **65 узлов, где масштаб сочетается с override** — размер в дереве и размер на
  холсте расходятся. Эталон — только рендер, не дерево.
- **236 из 1050 инстансов (22%) отмасштабированы**, у 405 (39%) переопределена
  геометрия. Это не дефект вёрстки, а состояние файла.
- **11 копий шапки, 27 блоков `min-width: 1200px`** в одном CSS — цена того, что
  единицей работы была страница.

И отдельно: секция «Практики» сошлась по высоте 916 = 916, а внутри стоял не тот
элемент — самодельная кнопка вместо инстанса `btn-primary`. Совпадение по высоте
скрывает подмену сущности; ловит её только сравнение компонента с кропом.

Главное: роли уже пробовали. В `syntonia-deepseek/docs/agent/` есть аудит, план,
правка и ревью. Не сработало не разделение труда, а **единица работы** (страница)
и **единица приёмки** (впечатление). Поэтому агентная система — это не «пять
персон», а контракты и ворота между ними.

Ещё один урок той сессии: знание о том, что дерево врёт, лежало в
`docs/FIGMA-ISSUES.md` пунктом 18 — и не попало в инструмент. Поэтому «мы это
знаем» не считается: знанием для агента является только то, что стало командой.

## 2. Четыре свойства, без которых это не система

1. **Контракт.** У каждой роли есть вход, выход и артефакт на диске. Агент не
   «передаёт мысли» другому агенту — он оставляет файл, который тот читает.
2. **Ворота.** Переход к следующей роли — только по команде с числом и кодом
   возврата. «Выглядит хорошо» не закрывает ворота.
3. **Свежий контекст на единицу работы.** Агент не помнит восемь часов истории:
   он получает карточку и три файла. Всё, что должно пережить сессию, лежит на
   диске.
4. **Знание живёт в команде.** Правило, которое нельзя проверить скриптом, агент
   не выполнит — даже если оно записано в документе. Поэтому каталог «файл врёт»
   превращается в проверки, а не в абзац.

## 3. Роли

| Роль | Миссия | Владеет | Не делает |
|---|---|---|---|
| **Владелец** (человек) | истина о контенте и приоритетах | `docs/decisions.md`, G0 | не верстает, не пишет CSS |
| **Дизайнер** (внешний) | чинить файл, а не последствия в коде | `.fig`: сброс масштабов, канонические фреймы, мобильные макеты | не пишет код |
| **Intake** (скрипты) | превратить `.fig` в факты | `extracted/`, `spec/`, `tokens.*`, `crops/`, `inventory.md`, `designer-fixes.md`, `changes.*` | не принимает дизайн-решений |
| **Продюсер** (оркестратор) | очередь, карточки, эскалации, журнал шагов | доска, `journal.md`, сводка `reports/` | не пишет код и не правит файлы сайта |
| **Верстальщик** (агент №1) | компонент и страница, проходящие ворота | `src/components/**`, `src/pages/**`, `reports/layout/**` | не решает неоднозначности, не принимает свою работу |
| **Приёмка** (QA) | независимо измерить и закрыть/вернуть | `reports/gates/**` | не правит код |
| **Адаптив** (позже) | 390/768: сначала инженерный слой, после макетов — по макету | адаптивные стили | не называет инженерный слой «по макету» |
| **Контент/бэкенд** (позже) | данные, CMS, формы | свои файлы | не трогают вёрстку |

Схема:

```
Владелец ──decisions.md──► Intake ──spec/tokens/crops──► Продюсер ──карточка──► Верстальщик
                                                                                   │
                                                    дефекты ◄── Приёмка ◄── diff + отчёт
                                                       │
                                                       └──► новые карточки
```

Продюсер стоит между доской и исполнителем: он решает, что делать следующим, и
разруливает конфликты файлов. Он не верстает — иначе повторяется первая сессия,
где один агент был и заказчиком, и исполнителем, и приёмщиком.

## 4. Контракты

| Артефакт | Кто создаёт | Кто читает | Инвариант |
|---|---|---|---|
| `design/figma/live/` | Intake | все | `fileKey` в `project.json`; без него отчёт — воспоминание |
| `reports/reality.md` | Intake | владелец, продюсер | по каждому 🔴 есть записанное решение до начала компонентов |
| `docs/decisions.md` | владелец | все | append-only; вопрос → варианты → решение → кто/когда |
| `spec/<page>.json` | Intake | верстальщик, приёмка | только факты; масштаб и override разрешены, эталон — рендер |
| `tokens.css`, `typography.css` | генератор | верстальщик | руками не правится |
| `crops/<component>.png` | Intake | верстальщик, приёмка | вырезан из экспорта канваса 1:1, а не из дерева |
| `designer-fixes.md` + `.csv` + `.extra.md` | Intake | дизайнер, владелец | каждый 🔴 имеет действие и узел; ручные находки не теряются |
| `changes.md` + `changes.agent.md` + `changes.json` | `figma-diff` | продюсер, верстальщик | сравнение двух выгрузок; триггер пересборки spec |
| `journal.md` | продюсер | владелец | шаги человеческим языком: что сделали и почему |
| карточка | продюсер | верстальщик, приёмка | заполнен Definition of Ready |
| `reports/layout/<card>.md` | верстальщик | приёмка, продюсер | числа и команды, а не «готово» |
| `reports/gates/G1-*.md` | приёмка | продюсер, владелец | exit code + таблица по компонентам |

Ворота — из [PROCESS.md](PROCESS.md): G0 (решения), G1
(компоненты), G2 (страницы), G3 (адаптив). Здесь важно разделение: **верстальщик
запускает проверки, но ворота закрывает приёмка.** Один и тот же агент не может
быть автором и судьёй — это не этика, а механика: он уже вложился в решение и
будет защищать его.

## 5. Документы: две версии

Правило, принятое 04.11: **у каждого документа две версии** — человеческая и
агентская. Человеческая объясняет «что это значит» и не содержит имён свойств
вроде `stackPositioning`; агентская содержит id узлов, свойства и «было → стало».
Если документ порождает проверку, рядом лежит JSON.

| Документ | Человеческая | Агентская | Кто пишет | Статус |
|---|---|---|---|---|
| Что изменилось в макете | `changes.md` | `changes.agent.md`, `changes.json` | `figma-diff` | есть |
| Правки для дизайнера | `designer-fixes.md` | `designer-fixes.csv` + `.extra.md` | `figma-fixes` + руками | есть |
| Шаги и объяснения | [`journal.md`](templates/journal.md) | — | продюсер | шаблон есть |
| Проблемы и варианты | разделы `designer-fixes.md`, `decisions.md` | `decisions.md` | владелец + агент | частично |
| Архитектура и подходы | `ARCHITECTURE.md` | `PROCESS.md` | человек + агент | частично |

Почему это не бюрократия: в первой сессии знание о масштабах лежало в
`FIGMA-ISSUES.md`, но не попало в инструмент; во второй правило «компонент не
знает, где стоит» знали, а `width: 303px` всё равно появился. Человеческий
документ нужен, чтобы решение можно было оспорить; агентский — чтобы оно
исполнялось одинаково. Один файл не бывает обоими: человеческий слишком расплывчат
для проверки, агентский нечитаем в перерыве.

Следствие для карточек: в отчёте сначала 2–3 предложения человеческим языком,
ниже — числа, команды и id. Шаблон отчёта обновлён.

**Версионность.** Любое число относится к конкретной выгрузке `.fig`. Новая
версия файла — это `figma-diff` → `changes.md` → пересборка `spec` и токенов.
В текущей версии Syntonia страница Library выросла с 159 до 806 элементов: если
этого не заметить, агент будет верстать по прошлой версии и «докажет»
соответствие тому, чего уже нет.

## 6. Верстальщик — почему первый

1. **Объём.** 18 наборов компонентов обслуживают все 7 страниц. Один верный
   компонент исправляет сорок мест; одна ошибка — тоже.
2. **Проверяемость.** Это единственная роль, чей результат можно оценить без
   вкуса: кроп-дифф, якоря в пикселях, высоты секций. Для сравнения, «контент» и
   «дизайн» так не проверяются.
3. **Здесь сгорело время.** 1604 вызова в первой сессии — это в основном рендер,
   замер, дифф, ещё замер. Работа механическая, но требует дисциплины, а не
   вдохновения.
4. **Ошибки уже каталогизированы.** `PROCESS.md` §7 («файл врёт») — готовый
   список ситуаций, на которые верстальщик обязан реагировать одинаково.

Полный устав: [agents/layout/AGENT.md](agents/layout/AGENT.md).
Готовый промпт запуска: [agents/layout/PROMPT.md](agents/layout/PROMPT.md).
Парная роль, без которой цикл не замыкается:
[agents/acceptance/AGENT.md](agents/acceptance/AGENT.md).

## 7. Как это запускается в DSH

### 7.1 Конституция проекта

`AGENTS.md` в корне сайта — единственный файл, который читается всеми агентами
автоматически. В нём: источники истины, границы, команды проверок, DoD, правила
остановки. `figma-layout-kit` остаётся отдельной папкой (решение 04.11): проект
ссылается на него, а не копирует внутрь. Устав верстальщика — дополнение к
конституции, а не замена.

Для `syntonia-v2` конституции пока нет; старый `syntonia-deepseek/AGENTS.md`
написан под страничную модель («одна задача — одна страница») и для нового
проекта не годится.

### 7.2 Одна карточка = один субагент

```
subagent(
  description: "layout: btn-primary",
  prompt: <PROMPT.md с подставленными путями>,
  cwd: ".../syntonia-v2"
)
```

Субагент получает свой контекст, `workspace-write` и `approvals: never` — это
ровно тот режим, в котором уже работал канбан-субагент. Он не видит историю
продюсера и не должен: вся память — в файлах.

Карточка, промпт и отчёт — шаблоны в [templates/](templates/).

### 7.3 Пачка карточек = workflow

Когда компоненты независимы, их можно гнать конвейером. Ключевое: сборка и
приёмка — **разные агенты**, поэтому приёмка не наследует контекст автора.

```js
const cards = args.cards;                       // карточки из бэклога
const results = await pipeline(cards,
  async (card) => agent(buildPrompt(card), {
    label: `${card.id}:build`, phase: 'build',
    schema: { type: 'object', properties: { status: { type: 'string' }, report: { type: 'string' } },
              required: ['status', 'report'], additionalProperties: true },
  }),
  async (built, card) => agent(qaPrompt(card, built), {
    label: `${card.id}:gate`, phase: 'gate',
    schema: { type: 'object', properties: { verdict: { enum: ['green', 'red'] }, defects: { type: 'array', items: { type: 'string' } } },
              required: ['verdict', 'defects'], additionalProperties: true },
  }),
);
return results;
```

Правило параллельности: две карточки одновременно — только если их списки
`files:` не пересекаются. Всё общее (`tokens.css`, `base.css`, шапка) меняется
отдельной карточкой и последовательно.

### 7.4 Goal — только у продюсера

В первой сессии цель с автопродолжением прокрутила 40 раундов, потому что
остановиться было некому: и исполнитель, и приёмщик — один агент. В этой схеме
`create_goal` ставит продюсер («G1 закрыт»), а верстальщик получает карточку и
стоп-условия. Карточка кончилась — работа кончилась.

### 7.5 Доска как общее состояние

Канбан — не отдельный сервис, а плагин DSH (`kanban-plugin/`): файл
`agent-system/board.json`, страница в левом меню и два инструмента агента
(`kanban_board`, `kanban_card`). Страница и агент пишут в один файл, поэтому
доска — общее состояние, а не отчёт одной из сторон.

Карточка несёт контракт (`unit`, `gate`, `spec`/`crop`/`figmaNode`, `files`,
`dod`, `report`). Переход из бэклога дальше проверяется по Definition of Ready;
`force: true` — только по явному решению человека. Колонки: бэклог → готово к
работе → в работе → на приёмке → готово.

Как это встроено в фазы и роли: [KANBAN.md](KANBAN.md). Установка и API:
`kanban-plugin/` — внешний плагин DSH, вне проекта.

### 7.6 Скил как упаковка, не как замена

Устав можно положить проектным скилом — `.dsh/skills/layout/SKILL.md`, — тогда
он подхватывается каталогом и не требует ручной ссылки в промпте. Но скил — это
инструкция: он не запускает ворота и не мешает агенту объявить себя готовым.
Полезен как переносимый текст между сайтами; дисциплину дают карточка, команда
проверки и отдельная приёмка.

## 8. План внедрения

Порядок важен: **сначала ворота, потом агенты.** Агент без ворот — это быстрый
способ произвести дрейф.

| Шаг | Что | Зачем | Оценка |
|---|---|---|---|
| 0 | `figma-resolve`: spec из рендера — масштаб и override разрешены, отклонения записаны | без него компоненты пишутся «по глазам» | 1 день |
| 1 | `/ds` из spec и 55 готовых кропов + `ds-check` → G1 | пилот цикла, а не сайта | 1 день |
| 2 | Одна секция (`formats`) полным циклом: карточка → верстальщик → приёмка | проверить контракт и стоп-условия | 0,5 дня |
| 3 | Три компонента параллельно; замерить конфликты и итерации | проверить параллельность | 0,5 дня |
| 4 | Перевести готовые секции `syntonia-v2` на библиотеку или переписать | убрать дрейф (`btn--hero { width: 303px }` и ещё три) | по объёму |
| 5 | Остальные страницы; адаптив — по макетам дизайнера | производство | по PROCESS.md |

Три оговорки, без которых план неверен:

- **G0 не обязан быть зелёным у дизайнера.** Достаточно, чтобы по каждому 🔴 было
  записано решение — включая «нормализуем к ближайшему варианту и фиксируем
  отклонение». Сейчас открыты два: масштабы (ждём дизайнера) и канонические
  фреймы Practice/Quiz.
- **Контент решено брать после сдачи сайта.** Это не блокирует вёрстку: значения
  из файла идут с пометкой «не подтверждено» и блокируют публикацию, а не карточку.
  В карточке это поле, а не стоп-условие.
- **Мобильные макеты заказаны.** До них G3 — инженерный слой (нет переполнения,
  тап-таргеты ≥ 44 px), после — обычный перенос по макету.

### Метрики

- итераций на карточку (цель ≤ 2);
- **escape rate** — сколько дефектов находит приёмка после «готово» (цель < 10%);
- время карточки;
- число `width/height` на месте вызова (цель 0);
- доля страниц, принятых с первого G2;
- открытые 🔴 в `decisions.md` старше недели.

Если escape rate высокий — виноват не агент, а Definition of Ready: карточка
недоговаривает.

## 9. Что система обязана исключить

| Наблюдённый провал | Механизм в системе |
|---|---|
| Страница как единица → 11 копий шапки | карточка = компонент; страницы только после G1 |
| Сверяли по дереву → требовали 249×44,7, которых на холсте нет | эталон — кроп из рендера; spec разрешает масштаб и override |
| Секция сошлась по высоте, внутри — не тот компонент | G1 по кропу каждого компонента, до страниц |
| `width: 303px` внутри варианта кнопки | запрет sizing на месте вызова + аудит |
| `fontSize: 48` при фактических 29 | правило «верить высоте узла и числу строк» |
| Знание было в `FIGMA-ISSUES.md` п.18, но не в инструменте | каждое правило каталога — проверка; документ вторичен |
| Новая выгрузка `.fig` осталась незамеченной (Library 159→806) | `figma-diff` → `changes.md` → пересборка spec |
| Повторяли «196×34» как улику, пока кроп не показал 182×32 | число без команды — фольклор; каждое число в отчёте воспроизводимо |
| Проверка в конце, ручная | ворота — команды с exit code, приёмка отдельная роль |
| 8,5 часов в одном контексте | свежий субагент на карточку, артефакты вместо памяти |
| Блок на 40-м раунде из-за цен и PNG | G0 и `decisions.md` до вёрстки; контент — отдельный трек |
| Параллельные сессии правят одно | `files:` в карточке, продюсер сериализует общее |

## 10. Что дальше

Соседняя сессия уже строит `figma-resolve` и `ds-check` — это шаги 0–1, и
дублировать их не нужно. Пока они не готовы, имеет смысл сделать то, что от них
не зависит:
