# Канбан в процессе

Версия 1.0 · 04.11.2026

Документ отвечает на вопрос «как встроить канбан в процесс», а не «как
пользоваться доской». Техническая часть — `kanban-plugin/` — внешний плагин DSH, вне проекта.
Процесс и роли — [README.md](README.md), ворота — [PROCESS.md](PROCESS.md).

---

## 1. Что было и почему убрали

04.11 в 20:50 в `syntonia-v2/kanban/` появился самостоятельный сервис: Node без
зависимостей, `server.mjs`, `GET/PUT /api/board`, страница с drag-and-drop.
3766 строк, всё проверено в браузере. В 21:35 он был удалён коммитом
`ca167fd` — после просьбы «убери канбан и поставь цель».

Причина не в доске. Причины в том, как она стояла:

- **отдельный сервер** — его надо было запускать, останавливать и держать
  живым рядом с DSH;
- **отдельная вкладка** — человек видел доску, агент её не видел: он ходил в
  неё `curl`-ом, если вообще ходил;
- **состояние в репозитории сайта** — доска про процесс лежала внутри проекта,
  который верстают;
- **карточка была заметкой**, а не контрактом: в ней не было `unit`, `gate`,
  `files`, `dod`. Процесс это уже сформулировал (README §7.5: «доска — вид,
  карточка — контракт»), но сервис этого не знал.

Вывод: проблема была не в интерфейсе, а в том, что доска стояла **сбоку** от
процесса. Плагин ставит её **внутрь** DSH.

## 2. Что такое плагин DSH

DSH — это Cordis-приложение: всё, что видно и работает, собрано из плагинов.
Плагин-«бандл» — обычный npm-пакет с двумя необязательными половинами:

| Половина | Что делает | Где живёт |
|---|---|---|
| **host** | сервисы, инструменты агента, HTTP-маршруты, файлы | в процессе DSH, рядом с сессиями |
| **client** | страницы и элементы Web UI | в браузере, в слотах интерфейса |

Связывает их `package.json`:

```json
"dsh": {
  "bundle": { "patch": "./cordis.patch.yml" },
  "client": { "platform": "web", "inject": ["@deepseek-ai/dsh-client-ui-layout"] }
}
```

`cordis.patch.yml` вставляет host-строку; клиентская половина подключается к
этой же строке по имени пакета. Поэтому установка одна, а не «сервер + сайт».

Три уровня интеграции, которые стоит различать:

1. **Отдельный сервис** (то, что было) — доска живёт сама по себе; агент и
   человек видят её только через браузер/curl. Никакой общности, кроме файла.
2. **Host-плагин** — доска внутри DSH, у агента есть инструменты, но человек
   видит её только через файл или чат.
3. **Плагин с клиентской страницей** — доска в интерфейсе DSH, у агента те же
   данные через инструменты. Это и есть «вписать в процесс», а не «рядом с
   процессом».

Скил — не замена: скил это инструкция, он не хранит общее состояние и не
рисует страницу. Скилом можно упаковать устав роли, но не доску.

## 3. Как устроен этот плагин

```
DSH Web
 ├─ слот main ──────────────► страница «Канбан» (client.js)
 │                                  │  GET  /kanban/api/board
 │                                  │  POST /kanban/api/op
 └─ host-плагин ────────────────────┘
        │
        ├─ tools: kanban_board, kanban_card  ◄── агент
        │
        └─ agent-system/board.json  ◄── один файл на всех
```

- Страница и агент ходят в **один файл**. Страница — через HTTP-маршруты
  плагина, агент — через инструменты. Запись атомарная, операции
  сериализованы, поэтому человек и агент не перезаписывают друг друга.
- Страница не хранит состояние у себя: каждые 2,5 секунды она перечитывает
  доску и показывает то, что на диске. Поэтому ход агента виден без
  перезагрузки.
- Инструменты возвращают не «готово», а данные: следующую карточку, список
  проблем контракта, колонки и счётчики.

Почему файл, а не база: доску можно смотреть в git, читать любым агентом без
плагина, переносить между профилями. Плагин — это интерфейс и проверки поверх
файла, а не хранилище, запертое в плагине.

## 4. Колонки, роли, правила

| Колонка | Что значит | Кто двигает дальше |
|---|---|---|
| **Бэклог** | идеи, вопросы, решения G0; контракт не требуется | человек или продюсер — в «готово к работе» |
| **Готово к работе** | Definition of Ready выполнен, можно брать | исполнитель — в «в работе» |
| **В работе** | один исполнитель, один набор файлов | исполнитель — в «на приёмке» |
| **На приёмке** | ждёт независимую проверку; автор не закрывает | приёмка — в «готово» или назад в «в работе» |
| **Готово** | ворота закрыты отчётом с exit code | — |

Правила, которые плагин умеет проверять:

1. **DoR.** Переход из бэклога дальше требует `unit`, `gate` и источника
   (`spec`, `crop` или `figmaNode`). Без них инструмент `kanban_card` вернёт
   `ok: false` и список проблем. `force: true` — только по явному решению
   человека; это не «настройка», а признак, что контракт нарушен осознанно.
2. **Предупреждения.** Пустые `files` и `dod` не блокируют перенос, но
   возвращаются в ответе: это первые кандидаты в дефекты приёмки.
3. **WIP.** Колонка «в работе» — не больше двух карточек, и только если их
   `files` не пересекаются. Плагин не считает это за вас; это правило
   продюсера (см. §7).
4. **Автор ≠ судья.** Приёмка — отдельный субагент, он читает карточку и
   отчёт, а не историю исполнителя.

### 4.1 Одна доска или несколько

Одна доска на проект. «Разделы» — это не доски, а разрезы одной доски: area
(`header`, `formats`, `library`, `voices`, `quiz`, `method`, `footer`, `ds`,
`tokens`, `infra`, `content`) и тип карточки (`fix`, `debt`, `feat`,
`decision`, `intake`, `acceptance`).

Почему не доска на раздел:

- у агента должен быть один ответ на «что дальше»; с пятнадцатью досками
  продюсер выбирает доску, а не работу;
- id и история карточки не переезжают между досками; перенос — потеря
  контекста;
- доски делят разные очереди с разными воротами и владельцами, а не участки
  одного сайта.

Когда всё-таки разделить: другой проект; другой жизненный цикл (контент с
приёмкой владельца против вёрстки с G1/G2); другой исполнитель, который не
должен видеть чужую очередь. И даже тогда — пока не болит, лучше одна доска и
фильтр.

В плагине сейчас один файл доски на установку. Второй проект — второй
`config.file` (второй профиль/установка) или будущее поле `boards` с
переключателем; это осознанно отложено. Поле `tag` работает как area, на
странице есть фильтр по нему; второй разрез (`kind`) добавим, когда фильтров
станет не хватать.

### 4.2 Карточка на доработку

Да, «взять элемент и написать карточку» — правильная единица. Но карточка —
не тема, а проверяемое изменение на один запуск.

Плохо: «Доработать блок formats» — агенту нечего проверять, он начнёт
улучшать по вкусу.

Хорошо:

- заголовок: `formats: сетка карточек — отступ 24 вместо 32`;
- описание: что видно, где, чем измерили, что должно быть (ссылка на кроп);
- `unit: formats`, `gate: G2`, `crop: ...`, `files: [Formats.astro, formats.css]`;
- `dod: [«отступ карточки 32 px», «высота секции 916 ± 2», «отчёт с числом»]`;
- `report: reports/layout/formats-grid.md`.

Три вида «доработок», и они не равны:

| Вид | Есть эталон? | Куда |
|---|---|---|
| дефект (не совпало с кропом/рендером) | да | карточка верстальщику, gate G1/G2 |
| долг (правило нарушено: width, hex, копия шапки) | правило/DoD | отдельная карточка долга, не смешивать с дефектом |
| «хочу иначе» | нет | сначала решение G0 в `decisions.md`, потом карточка |

Третья строка — главная защита от дрейфа. AGENTS.md §2.7 уже требует не
додумывать; карточка без эталона это правило обходит.

Нарезка: один блок = одна карточка, если правки в одних файлах и одна
приёмка. Пять независимых дефектов — пять карточек (или одна с чек-листом,
если правка одна). Долг и правку текста не смешивать — это и правило git.

### 4.3 Откуда берутся карточки после первой версии

После того как главная собрана, бэклог наполняется не желаниями, а фактами:

1. **Аудит секций**: текущий рендер против кропа, снятого с живого узла, по каждому
   отклонению — карточка-дефект с числом.
2. **Долг из AGENTS.md §10**: семь `width` в Button, `tokens.css`, отсутствие
   `/ds`, неподключённые spec/crops — по карточке на пункт.
3. **Решения G0**: масштабы, канонические фреймы, контент — карточки с
   `assignee: human`.
4. **Найдено по пути**: агент нашёл дефект вне `files:` — заводит карточку,
   а не расширяет правку.

## 5. Контракт карточки

```json
{
  "id": "c-4f2a1b",
  "title": "Кнопка btn-primary по кропу",
  "description": "Собрать вариант кнопки из инстанса, сверить с кропом 1:1.",
  "column": "ready",
  "assignee": "agent",
  "priority": "high",
  "tag": "layout",
  "unit": "btn-primary",
  "figmaNode": "123:456",
  "spec": "design/figma/pages/home/hero/spec.json",
  "crop": "design/figma/pages/home/hero/crop.png",
  "gate": "G1",
  "report": "reports/layout/btn-primary.md",
  "files": ["src/components/Button.astro", "src/styles/tokens.css"],
  "dod": [
    "совпадает с кропом по размеру и цвету",
    "нет width/height на месте вызова",
    "отчёт с числами и командами"
  ]
}
```

`history` ведёт плагин: кто и когда создал, менял, двигал. Это не заменяет
`journal.md` — история машинная, журнал человеческий.

## 6. Как встроить в P0–P7

| Фаза | Карточки | gate |
|---|---|---|
| P0 — решения | вопросы дизайнеру и владельцу: масштабы, канонические фреймы | G0 |
| P1 — intake | выгрузка `.fig`, spec, токены, кропы | — |
| P2–P4 — компоненты | по одной карточке на `unit`; `files` — компонент и его стили | G1 |
| P5 — страницы | сборка секций из принятых компонентов | G2 |
| P6–P7 — адаптив | 390/768, сначала инженерный слой | G3 |

Правило прежнее: **сначала ворота, потом агенты**. Карточка не делает ворота
зелёными; она лишь говорит, что именно проверять и чем закрывать.

Где доска не заменяет процесс:

- `decisions.md` остаётся append-only источником решений; карточка ссылается
  на решение, а не пересказывает его;
- отчёт приёмки — файл с exit code, а не карточка;
- `journal.md` объясняет шаги человеку; `history` карточки — только факты.

## 7. Промпт продюсера и исполнителя

Продюсер в начале хода:

```text
Прочитай доску: kanban_board { next: true, assignee: "agent" }.
Возьми первую карточку, проверь Definition of Ready.
Если проблем нет — переведи её в progress и запусти исполнителя субагентом.
Если проблемы есть — верни карточку в backlog с комментарием или эскалируй.
```

Исполнитель получает не историю, а карточку и три файла (spec, crop, устав).
В конце:

```text
kanban_card {
  action: "move", cardId: "<id>", column: "review",
  report: "reports/layout/<card>.md"
}
```

Приёмка:

```text
Прочитай карточку и отчёт, прогони ворота.
Зелёный — move в done; красный — move назад в progress и список дефектов.
```

Важно: `kanban_card` — единственный путь менять доску агентом. Если агент
правит `board.json` напрямую `write`-инструментом, он обходит DoR и историю.

## 8. Установка и проверка

1. DSH Web → **Plugins** → **Add plugin** → абсолютный путь:

   ```
   path/to/kanban-plugin
   ```

2. **Install** → **Enable now**. В меню появится **Канбан**.
3. Добавьте карточку на странице. Файл
   `agent-system/board.json` создастся сам.
4. Проверьте, что агент видит ту же доску: в новом ходе попросите
   `kanban_board { next: true }` — он должен вернуть вашу карточку.

Если порт DSH другой, возьмите его из адресной строки; host-проверка:

```bash
curl -s http://127.0.0.1:57686/kanban/api/board | python3 -m json.tool | head
```

Ограничения, которые лучше знать заранее:

- маршруты плагина не проходят браузерную аутентификацию DSH: это локальный
  loopback-сервер, любой процесс на машине может писать в доску. Для
  локальной работы приемлемо; для публичного хоста — нет;
- страница работает только в Web (не в Desktop и не в TUI);
- одна установка — одна доска; для второго проекта меняется `config.file`
  в `cordis.patch.yml` (или ставится второй профиль);
- приёмка не автоматизирована: плагин маршрутизирует, но не запускает
  ворота. Это следующий шаг, а не свойство доски.

## 9. Что дальше

- **Карточка как файл.** `cards/<id>.md` рядом с `board.json`: контракт
  диффится в git, доска остаётся индексом. Плагин уже хранит все поля, так
  что переход не ломает страницу.
- **Инструмент приёмки.** `kanban_gate` запускает команду ворот и пишет
  отчёт; карточка не может попасть в `done` без exit code 0.
- **Несколько досок.** `boards` в конфиге и переключатель проекта на
  странице.
- **Аутентификация маршрутов.** Токен в `config`, если DSH перестанет быть
  loopback-only.

Метрики, по которым видно, что доска работает: итераций на карточку (≤ 2),
escape rate приёмки (< 10%), карточки без `files` (0), WIP > 2 (0), время
карточки.
