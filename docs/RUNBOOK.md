# Запуск нового сайта

Полный протокол прогона с кодами и артефактами — [`COLD-START.md`](COLD-START.md).

Один и тот же конвейер для любого сайта. Меняется **один файл** —
`design/figma/project.json`, и то не целиком: страницы и фреймы в него пишет
`npm run discover` из самого файла.

Ниже — прогон от пустой папки до страницы структуры. Каждый шаг: команда,
код возврата, файл на диске.

## 0. Что нужно

- Figma открыта, в ней нужный файл, мост подключён (`figma-agent status`);
- Node и `npm`;
- папка с одним каталогом `tools/` — больше ничего не нужно.

## 0.0 Включить хуки

```bash
npm run hooks
```

Ставит `core.hooksPath` на `tools/git-hooks`. После этого каждый коммит сам
уходит на GitHub, если он доступен; если нет — коммит остаётся локальным и хук
печатает, как отправить позже. Хук не блокирует коммит никогда.

**Порядок обязателен.** `npm run build` проверяет сгенерированные файлы и
падает с подсказкой, а не с `Module not found`:

```
intake → ds:tokens → structure → build
```

Каждый шаг зависит от предыдущего: без `intake` нет снимка файла, без него нет
токенов, без токенов не собирается страница.

## 0.1 Развернуть каркас

```bash
node tools/scaffold.mjs
npm install
```

Кладёт `astro.config.mjs`, `tsconfig.json`, `package.json`, каркас страницы
(`src/layouts/BaseLayout.astro`, `src/styles/base.css`) и саму страницу структуры
(`src/pages/structure.astro`). Шаблоны лежат в `tools/scaffold/` и не знают ни про
какой проект: имя файла, страницы и кадры приходят из `project.json`.

Существующие файлы не перезаписываются — нужен `--force`.

## 1. Что меняется для нового сайта

Один файл — `design/figma/project.json`. Код и инструкции не трогаются.

| ключ | что задаёт | откуда берётся |
|---|---|---|
| `source.fileKey`, `source.fileName` | какой файл считается истиной; `intake` сверяет и падает, если открыт другой | `discover --write` |
| `pages` | какие страницы выгружать; убрать ключ — страница исчезнет из карты | `discover --write` |
| `frames` | какой кадр страницы считать страницей, а не блоком | `discover --write` |
| `designSystemPage` | страница витрины компонентов; её кадры — образцы, а не макеты | `discover --write` |
| `gates.geometryTolerancePx`, `gates.pixelDelta` | допуски замера и пикселя | по умолчанию 1 px и 16 |
| `paths.*` | где лежат снимки, спеки, ассеты, экраны | по умолчанию `design/figma/**` |
| `routes` | адрес каждой страницы для сверки | заполняется под проект |
| `api.tokenFile` | где лежит токен REST; **в корне проекта**, не у соседа | по умолчанию `.figma-token` |

Проверено: смена `source.fileName` меняет страницу структуры без правок кода;
удаление `pages.booking` убирает страницу из карты. Оба раза правился только JSON.

**Граница автоматизации.** Конвейер доводит новый проект до карты секций,
экспортированной секции и проверенных ассетов. Дальше начинается работа
агента: собрать компонент по `spec.json`.

Начать её можно с черновика: `npm run gen -- plan <page>/<section>`, затем

`AGENTS.md` §9.07, числа в `docs/GEN-CALIBRATION.md`.

**Проверено, что проект задаётся одним JSON:** в той же папке поменяли

появилось на странице, старое исчезло. Код не трогали.

`tools/scaffold/**` с проектом и состав команд. Именно на этом и поймали
разрыв — шаблон разворачивал Astro `^5` при установленном 7.4.5 и не содержал
`variants`, `bindings`, `motion`, `interactive`, `tokens:check`.

## 2.1 Шрифты

```bash
npm run fonts          # скачать woff2 и записать public/fonts/fonts.css
npm run fonts:check    # только сверить, что файлы на месте (без сети)
```

Семьи, веса и курсив берутся из **текстовых стилей живого файла**
(`design/figma/live/reality.json`), а не из списка в коде. Подмножества
(cyrillic, latin, ext) сохраняются отдельными файлами — браузер грузит нужное.

Проверено на пустой папке (08.11.2026): 6 начертаний, 31 файл, `fonts.css`
записан; `fonts:check` — 0. В проекте: 6 начертаний, 33 файла, 624 КБ,
на сайте грузятся 11 начертаний, ворота зелёные.

Без этого шага сайт соберётся, но на системных шрифтах: `verify` пройдёт,
а выглядеть будет иначе.

## 2.2 Манифест движения

```bash
npm run motion:manifest
```

Пишет `design/motion/motion.json` — все правила с движением из `src/styles`.
Каждой записи нужен `decision`: движение без записи считается нерешённым, и
`motion:check` краснеет. Это не ошибка конвейера, а требование решения.

## 3. Страницы и фреймы — в JSON

```bash
npm run discover -- --write
npm run discover -- --check
```

Первый раз заполняет `pages` и `frames`. Канонический фрейм — тот, что называется
`main`, иначе первый непустой. Остальные фреймы страницы (журнальные выпуски,
результаты теста) в работу не идут, но остаются в отчёте `discover`.

`--check` — сверка без записи: `exit 1`, если страницу переименовали или
удалили. Это дешёвая проверка «JSON ещё описывает файл».

**Выход:** `design/figma/project.json` с `source`, `paths`, `gates`, `pages`, `frames`

Проверено: папка с одним `tools/` и открытым файлом — `discover --write` создаёт
JSON целиком (8 страниц), дальше `intake` и `structure` дают карту из 46 секций
без единой правки руками.

## 10. Проверка одной командой

```bash
npm run conveyor -- check --all          # все секции, которые уже в конвейере
npm run conveyor -- check --unit home/hero   # одна секция с пикселем
```

Все ворота подряд, без срезания: упавшая проверка не скрывает следующие.
Итог — один из четырёх статусов и каталог прогона.

```
вердикт: PASS
прогон: reports/runs/20261107-090126-69485/
```

| статус | что значит | код |
|---|---|---|
| `PASS` | всё измерено и чисто | 0 |
| `FAIL` | проверка выполнена и нашла дефект | 1 |
| `INCOMPLETE` | ничего не сломалось, но часть не измерена | 2 |
| `ERROR` | инструмент не смог выполниться | 2 |

Порядок не симметричен: `FAIL` сильнее `INCOMPLETE` — сломанная сборка это
определённость, а не «неизвестно».

Пиксель (`compare`) идёт как `signal`: он диагностика и в вердикт не входит.
В режиме `--all` пиксель не снимается — он нужен для разбора одной секции, а
не для прогона по всей странице.

**В новом проекте `check` сначала будет красным** — и это правильно: собирать
ещё нечего, проверять нечего. Порядок такой: `structure` даёт карту, дальше
строятся блоки, и только потом `check` становится зелёным. `check --all`
проверяет не «всё, что есть в файле», а «всё, что уже собрано».

**Контент всех состояний.** `npm run states` сверяет тексты из `states.json`
с тем, что реально на странице. Если секция живёт в нескольких состояниях с
разным контентом (карусель отзывов, вкладки форматов, аккордеон), каждый текст
обязан быть в вёрстке. Проверка берёт только состояния той же страницы: у
подвала они приходят с других страниц, и требовать их на главной нельзя.

Секция попадает в `--all`, если у неё есть `gate.json`: это значит, что она уже
собрана и замерялась. Несобранные секции в прогон не входят и вердикт не
портят — но и не притворяются проверенными.

Что ещё умеет:

```bash
npm run conveyor -- plan --unit home/hero   # показать шаги, ничего не выполняя
npm run conveyor -- status                  # итог последнего прогона
npm run conveyor -- status --json           # то же машинно, в stdout
```

Каждый прогон — отдельный каталог `reports/runs/<runId>/` с `verdict.json`,
`events.jsonl` и `results/<шаг>.json`. Один прогон не затирает доказательства
другого: `gate.json` рядом со спекой перезаписывается, история прогонов — нет.

## 11. Проверка, что всё сходится

```bash
npm run verify
```

Сверяет: экспорт ↔ мост (отпечатки), экспорт ↔ облако (версия), структуру с
API, картинки и тексты с `.fig`. Недоступность вспомогательного источника —
пропущенная сверка, не провал.

## Что делает проект «другим сайтом»

| Меняется | Где |
|---|---|
| `fileKey`, имя файла | `project.json` → `source` (или `discover --write`) |
| страницы и фреймы | `project.json` → `pages`, `frames` (**автоматически**) |
| маршруты страниц | `project.json` → `routes` |
| допуски ворот | `project.json` → `gates` |
| пути | `project.json` → `paths` |

Код и скилы не меняются. Если для нового сайта пришлось править `tools/` или
скил — значит конвейер ещё не универсален, и правка идёт в конвейер, а не в
конкретный сайт.

## Второй адрес: пре-публикация

Кроме основного зеркала есть репозиторий `synt-prepublicate` — в нём лежит и
мастерская (ветка `main`), и собранный сайт (ветка `site`):

| | |
|---|---|
| сайт | https://appacc77-dotcom.github.io/synt-prepublicate/ |
| мастерская | https://github.com/appacc77-dotcom/synt-prepublicate (main) |
| выпуск | та же репозитория, ветка `site` |

Адрес не в корне домена, поэтому выпуск собирается с префиксом пути:

```bash
node tools/site-export.mjs --base /synt-prepublicate --push \
  --mirror https://github.com/appacc77-dotcom/synt-prepublicate.git --mirror-branch site
```

`--base` переписывает абсолютные адреса в сборке (`href`, `src`, `url()` в CSS):
без него картинки и стили уезжают на корень домена и дают 404 — на этом
сломалась первая публикация.
